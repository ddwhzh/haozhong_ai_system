## 1. 系统总览

昊中多Agent系统是一个基于LangGraph状态机编排的生产级AI Agent应用, 采用管理式金字塔架构分层设计, 通过多阶段管道(Classify(QDMR) → Explore(Tree+Backtrack) → Freeze → Plan → Execute → Validate → Done/Rollback)实现从查询到高质量结构化回答的完整流程.

> 
> 本文档为系统级功能总览.

### 1.1 核心架构

系统采用**管理式金字塔架构分层**设计:

- **编排层 (Orchestration Layer)**: LangGraph状态机管理整个管道流程, Gateway节点负责路由决策
- **Agent层 (Agent Layer)**: 三个专业Agent (Retrieval, Generation, Evaluation) 各自负责特定阶段
- **基础设施层 (Infrastructure Layer)**: LLM服务, 向量数据库(PGVector), 知识图谱(Neo4j), 持久化存储

### 1.2 状态机流程

系统遵循严格的状态机编排, 确保可追溯性和可控性:

```
Explore (检索) → Freeze (上下文快照) → Plan (提案分解) → Execute (内容生成) → Validate (评估) → Done/Rollback
```

每个阶段完成后通过Gateway节点进行路由决策, 支持回滚和人工审核(HITL)机制.

## 3. 检索Agent功能详细说明 (F-3a ~ F-5)

检索Agent负责**Explore阶段**, 采用QDMR查询分类 + 树形探索 + 分支回退的新架构, 替代旧的平铺子查询并行检索:

```
新管道: Query -> Classify(QDMR) -> QDMR Decompose -> TreeExplore(逐步/逐分支/回退) -> Cascade
旧管道: Query -> Decompose -> [RAG+KG并行] -> Cascade
```

### 3.0 QueryClassifier — QDMR查询分类 (F-3a)

**功能**: 基于QDMR将查询分为8个类别, 每个类别决定最优检索策略配置.

#### 8类QDMR查询分类

| QType | 含义 | 主策略 | 备选策略 | 分解深度 | 典型查询 |
|-------|------|--------|---------|---------|---------|
| QSelect | 简单事实查询 | RAG | KG | 2 | "什么是知识图谱?" |
| QFilter | 条件过滤查询 | RAG | KG | 2 | "哪些图神经网络支持大规模训练?" |
| QChain | 链式推理查询 | KG | RAG | 3 | "发明Transformer的团队在哪家公司?" |
| QComposition | 组合查询 | both | both | 3 | "解释知识图谱并比较其与向量数据库的区别" |
| QComparison | 比较查询 | both | both | 3 | "BERT和GPT的区别是什么?" |
| QAggregation | 聚合/排序查询 | KG | RAG | 2 | "列出最常用的图数据库" |
| QBoolean | 是否判断查询 | RAG | KG | 1 | "Neo4j是否支持全文检索?" |
| QUnion | 联合/交叉查询 | both | both | 3 | "知识图谱在医疗和金融领域的应用" |

#### 输入输出

- **输入**: `query` (str), `evidence_graph` (EvidenceGraph)
- **输出**: `ClassificationResult` + `EvidenceNode` (content_type="query_classification")
- ClassificationResult包含: `q_type`, `confidence`, `reasoning`, `decomposition_hint`, `strategy`

#### 实现文件

- 分类器: `app/agents/retrieval/query_classifier.py`
- Prompt: `app/prompts/query_classify_system.md`

### 3.0b TreeExplorer — 树形探索 + 分支回退 (F-3c)

**功能**: 给定QDMR分解步骤, 逐步骤执行检索, 支持分支级回退.

#### 树结构

```
根节点 (分类结果)
  -> Step 1 (QDMR步骤1)
       -> Branch A (主策略, 如RAG)
       -> Branch B (备选策略, 如KG)  [仅在A回退时执行]
  -> Step 2 (QDMR步骤2)
       -> Branch A
       -> Branch B
```

#### 分支回退算法

1. 对每个TreeStep, 执行主策略(primary_strategy)
2. 评估分支质量 = 结果节点置信度均值
3. 如果 quality < backtrack_threshold (默认0.4):
   - 回退到备选策略(fallback_strategy)
   - 再次评估质量
   - 保留质量更好的结果(或合并两者)
4. 最多回退 max_branch_retries 次(默认1)

#### 配置项

| 环境变量 | 默认值 | 含义 |
|---------|--------|------|
| `RETRIEVAL_BACKTRACK_THRESHOLD` | 0.4 | 分支质量回退阈值 |
| `RETRIEVAL_MAX_BRANCH_RETRIES` | 1 | 每步最大回退次数 |
| `RETRIEVAL_MAX_TREE_DEPTH` | 3 | 最大树深度(QDMR分解步骤数) |

### 3.1 QueryDecomposer — 查询分解 (F-3b)

**功能**: 支持两种模式: 经典平铺分解(旧) + QDMR类型感知分解(新).

#### QDMR分解模式 (新)

- **方法**: `qdmr_decompose(query, q_type, max_steps)`
- **输入**: query (str), q_type (QType), max_steps (int)
- **输出**: `List[TreeStep]`, 每个TreeStep包含:
  - `step_idx`: 步骤序号
  - `question`: 步骤子问题
  - `operator`: QDMR算子(select, filter, project, aggregate, compare, union, intersect, sort, boolean)
  - `retrieval_strategy`: 建议检索策略("rag", "kg", "both")
  - `depends_on`: 依赖的前置步骤索引列表
- **Prompt**: `app/prompts/qdmr_decompose_system.md` (类型感知指导)

#### 经典分解模式 (保留)

- **方法**: `decompose(query, evidence_graph)`
- **输出**: `List[EvidenceNode]` (根查询 + 子查询节点)

3. **构建子查询节点**:
   - 每个子查询创建独立的EvidenceNode
   - 通过`DECOMPOSES_TO`边连接到根节点
   - 子查询可并行执行, 互不依赖

4. **降级策略 (Fallback)**:
   - 如果LLM调用失败, 将原始查询作为唯一子查询继续执行
   - 记录错误日志, 但不中断管道

#### Prompt文件

- **位置**: `app/prompts/query_decompose_system.md`
- **内容**: 要求LLM将复杂查询分解为独立可搜索的子查询, 保持多样性, 避免冗余

#### 可配置项

- `RETRIEVAL_MAX_SUB_QUERIES`: 最大子查询数量(默认5)

### 3.2 VectorRetriever — 广度检索管道(向量/混合) (F-3补充)

**功能**: 对每个`sub_query/tree_step`执行PG检索, 支持:

- Dense模式: PGVector余弦相似度检索
- Hybrid模式: Dense + Sparse(关键词ILIKE)并用加权RRF融合排序

#### 输入输出

- **输入**: 
  - `sub_query_nodes` (List[EvidenceNode]): 子查询或树步骤节点列表
  
- **输出**: 
  - `List[EvidenceNode]`: 文档片段节点列表
  - `content_type="document_chunk"`, `confidence=相似度分数`

#### 处理流程

1. **Embedding生成**:
   - 对每个子查询调用OpenAI Embeddings API
   - 使用模型: `embedding-3` (配置项`EMBEDDING_MODEL`)

2. **检索执行**:
   - **Dense模式**:
     - 在PGVector数据库中执行余弦相似度搜索
     - 排序: `ORDER BY embedding <=> query_embedding LIMIT top_k`
   - **Hybrid模式**:
     - Dense候选: 余弦相似度TopN
     - Sparse候选: 基于query关键词对 `content` 执行 `ILIKE` 匹配打分
     - 融合: 使用加权RRF(Reciprocal Rank Fusion)合并排序
     - 输出同时带 `dense_score/sparse_score/dense_rank/sparse_rank`
   - 查询目标表: `documents` (`VECTOR_COLLECTION_NAME`配置)
   - 返回top_k个结果(默认`RETRIEVAL_TOP_K=10`)

3. **构建证据节点**:
   - 每个检索结果封装为EvidenceNode
   - `confidence = cosine_similarity_score` (0.0~1.0)
   - `intent = RETRIEVE`
   - 通过`DERIVED_FROM`边连接到对应的子查询节点

#### 技术细节

- **向量模型**: OpenAI `text-embedding-3-small` 或 `text-embedding-3-large`
- **相似度度量**: 余弦相似度 (cosine similarity)
- **数据库**: PostgreSQL + pgvector扩展
- **混合检索融合**: Weighted RRF

#### 可配置项

- `RETRIEVAL_TOP_K`: 每个子查询返回的top结果数(默认10)
- `RETRIEVAL_VECTOR_MODE`: `dense` 或 `hybrid`
- `RETRIEVAL_HYBRID_DENSE_WEIGHT`: Hybrid中Dense权重(默认0.6)
- `RETRIEVAL_HYBRID_SPARSE_WEIGHT`: Hybrid中Sparse权重(默认0.4)
- `RETRIEVAL_HYBRID_RRF_K`: RRF平滑参数(默认60)
- `RETRIEVAL_HYBRID_CANDIDATES`: Hybrid融合前每路候选数(默认30)
- `RETRIEVAL_HYBRID_MAX_TERMS`: Sparse关键词最大数量(默认8)
- `EMBEDDING_MODEL`: Embedding模型名称

### 3.2b BraveWebRetriever — Web检索补充与跨轮RAG沉淀 (F-3d)

**功能**: 在树形探索阶段引入Brave检索结果, 并可选将Top结果自动沉淀到PGVector以供后续RAG召回.

#### 进入链路(同轮)

1. `TreeExplorer._execute_branch()` 在以下场景调用Brave:
   - 分支策略为`rag/both`时, 在向量检索后追加Web检索。
   - 分支策略为`kg`且KG无结果时, 启用Web回退补充证据。
2. Brave结果写入证据图:
   - `content_type="web_result"`
   - metadata含: `title/url/snippet/rank/query/engine`
3. 检索Agent汇总时:
   - `breadth_nodes = document_chunk + web_result`
   - `depth_nodes = kg_match + reasoning_chain`
   - 两者共同参与Cascade融合。

#### 沉淀链路(跨轮)

开启`BRAVE_AUTO_INDEX_TO_VECTOR=true`后:

1. 对Top N Brave结果生成embedding。
2. upsert到PGVector `documents` 表。
3. metadata写入 `source_type=brave_search` 等来源信息。
4. 后续查询由`VectorRetriever`检索出来时, 表现为`document_chunk`节点。

#### 与KG边界

- 当前实现**不会**将Brave结果直接写入Neo4j。
- Brave与KG关系是“证据互补”而非“数据同化”:
  - KG负责结构关系和多跳链路。
  - Brave负责外部新鲜信息补充。

#### 配置项

- `BRAVE_SEARCH_ENABLED`
- `BRAVE_SEARCH_API_KEY`
- `BRAVE_SEARCH_TOP_K`
- `BRAVE_AUTO_INDEX_TO_VECTOR`
- `BRAVE_AUTO_INDEX_MAX_ITEMS`
- `BRAVE_AUTO_INDEX_MIN_CONTENT_CHARS`

#### 详细说明文档

- `docs/agents/retrieval-agent/2026-02-10-v1.1-Brave结果进入RAG与KG链路详解.md`

### 3.3 KGRetriever — KG BFS深度检索 (F-4)

**功能**: 通过Neo4j知识图谱进行双向CONTAINS匹配和BFS多跳扩展, 构建推理链.

#### 输入输出

- **输入**: 
  - `sub_query_nodes` (List[EvidenceNode]): 子查询节点列表
  
- **输出**: 
  - `List[EvidenceNode]`: 推理链节点列表
  - `content_type="reasoning_chain"` 或 `"kg_match"`

#### 处理流程

**阶段1: 实体链接 (Entity Linking)**

1. **双向CONTAINS匹配**:
   - 在Neo4j中执行全文搜索: `MATCH (n) WHERE n.name CONTAINS $text OR n.description CONTAINS $text`
   - 同时支持正向匹配(查询文本包含实体名)和反向匹配(实体名包含查询文本)
   - 限制: `search_limit=10`个初始匹配

2. **构建KG匹配节点**:
   - 每个匹配的实体创建`kg_match`类型节点
   - 置信度随排名衰减: `confidence = max(0.6, 0.9 - rank * 0.05)`
   - 包含实体标签, 属性, 描述等信息

**阶段2: BFS多跳扩展**

3. **BFS遍历**:
   - 从种子实体(匹配的实体)出发, 执行广度优先搜索
   - 最大跳数: `RETRIEVAL_KG_MAX_HOPS` (默认3跳)
   - 每跳限制: `limit_per_hop=15`个节点

4. **关系路径收集**:
   - 收集所有从种子实体出发的路径
   - 路径格式: `(Entity1)-[REL1]->(Entity2)-[REL2]->(Entity3)`

**阶段3: 推理链拆分**

5. **子图拆分为推理链**:
   - 将BFS返回的大子图按种子实体拆分为线性路径
   - 每条路径即一条推理链: `[Entity1] -> [Entity2] -> [Entity3]`
   - 目的: 让下游Agent能"读懂"多跳推理逻辑

6. **构建推理链节点**:
   - 每条推理链封装为`reasoning_chain`类型节点
   - 内容格式: 文本化的实体-关系路径
   - 置信度基于路径长度和实体匹配度计算

#### 技术细节

- **Neo4j查询**: 使用Cypher查询语言
- **BFS算法**: 自定义BFS实现, 支持多跳限制和每跳节点数限制
- **推理链格式**: `[Label:Name] -> [Relationship] -> [Label:Name]`

#### 可配置项

- `RETRIEVAL_KG_MAX_HOPS`: BFS最大跳数(默认3)
- `limit_per_hop`: 每跳最大节点数(默认15)
- `search_limit`: 初始实体匹配数量(默认10)

### 3.4 CascadeFuser — 多轮融合 (F-5)

**功能**: 迭代融合广度检索(RAG + Web)和深度检索(KG)的结果, 识别信息缺口并补全.

#### 输入输出

- **输入**: 
  - `query` (str): 原始用户查询
  - `breadth_nodes` (List[EvidenceNode]): 广度检索结果(`document_chunk` + `web_result`)
  - `depth_nodes` (List[EvidenceNode]): KG检索结果
  
- **输出**: 
  - `List[EvidenceNode]`: 融合后的证据节点列表
  - `content_type="fused_evidence"`

#### 处理流程

**多轮迭代融合**

1. **第1轮: 初始融合**
   - 收集所有检索结果(广度+深度)
   - 调用LLM评估:
     - `relevance_score`: 相关性得分(0.0~1.0)
     - `completeness_score`: 完整性得分(0.0~1.0)
     - `gaps`: 识别的信息缺口列表
     - `fused_summary`: 融合后的摘要文本
     - `reasoning`: 融合推理过程

2. **提前停止条件**:
   - 如果`completeness_score >= 0.85`, 提前停止融合
   - 记录日志: `cascade_early_stop`

3. **后续轮次**:
   - 将上一轮的融合结果纳入下一轮上下文
   - 继续评估缺口并补全
   - 最多执行`RETRIEVAL_CASCADE_ROUNDS`轮(默认3轮)

4. **构建融合节点**:
   - 每轮创建一个`fused_evidence`节点
   - `confidence = (relevance + completeness) / 2.0`
   - 元数据包含: `round`, `relevance`, `completeness`, `gaps`, `reasoning`
   - 通过`FUSED_INTO`边连接到所有源节点

#### Prompt文件

- **位置**: `app/prompts/cascade_fusion_system.md`
- **功能**: 指导LLM评估证据相关性, 完整性, 识别缺口, 生成融合摘要

#### 缺口检测机制

- LLM分析当前证据是否完整回答查询的所有方面
- 识别缺失的信息类型(如: 缺少时间信息, 缺少因果关系等)
- 将缺口列表传递给下一轮融合

#### 可配置项

- `RETRIEVAL_CASCADE_ROUNDS`: 最大融合轮数(默认3)

## 4. 生成Agent功能详细说明 (F-6)

生成Agent负责**Plan和Execute阶段**, 采用Fast RCNN启发的两阶段设计: Proposal分解 → 证据图槽位填空.

### 4.1 ProposalDecomposer — Proposal分解 (Stage 1)

**功能**: 生成N个同结构的proposal节点, 每个proposal定义需要从证据图中提取的槽位.

#### 核心设计理念

**关键区别**: 这不是模板模式, 而是**槽位提取模式**.

- **模板模式(旧)**: LLM按模板自由生成文本
- **槽位提取模式(新)**: Proposal定义"从证据图中提取什么", 而非"按什么模板写"
- **优势**: 
  - 粒度一致: 所有proposal相同结构 = 所有输出相同粒度
  - 提取 > 生成: 每个slot从证据图节点中提取, 不凭空生成
  - 可追溯: 每个filled slot记录`source_evidence_ids`

#### 输入输出

- **输入**: 
  - `query` (str): 用户查询
  - `evidence_graph` (EvidenceGraph): 检索阶段构建的证据图
  
- **输出**: 
  - `List[EvidenceNode]`: Proposal节点列表
  - `content_type="proposal"`

#### Proposal结构

每个proposal是JSON格式, 包含以下字段:

```json
{
  "aspect": "定义",
  "question": "什么是知识图谱?",
  "slots": [
    {
      "name": "核心定义",
      "description": "一句话定义",
      "evidence_hint": "fused_evidence"
    },
    {
      "name": "关键特征",
      "description": "核心特征",
      "evidence_hint": "kg_match"
    },
    {
      "name": "支撑证据",
      "description": "具体证据",
      "evidence_hint": "document_chunk"
    }
  ],
  "priority": 1
}
```

**字段说明**:
- `aspect`: 回答的方面(如"定义", "应用", "关系")
- `question`: 该方面对应的具体问题
- `slots`: 槽位列表, 每个槽位包含:
  - `name`: 槽位名称
  - `description`: 需要提取的信息描述
  - `evidence_hint`: 证据类型提示(`fused_evidence`, `kg_match`, `document_chunk`, `any`)
- `priority`: 优先级(1最高, 5最低)

#### 处理流程

1. **证据摘要**:
   - 收集高置信度节点(`confidence >= 0.3`)
   - 生成证据摘要文本(最多15个节点)
   - 统计各类型证据数量

2. **LLM生成Proposals**:
   - 使用prompt文件 `proposal_decompose_system.md`
   - 输入: 用户查询 + 证据摘要 + 证据统计
   - 输出: JSON数组, 最多`GENERATION_MAX_PROPOSALS`个(默认5)

3. **构建Proposal节点**:
   - 每个proposal创建EvidenceNode
   - 元数据包含: `aspect`, `question`, `slot_count`, `priority`, `index`
   - `confidence=0.85` (固定值, 因为这是规划阶段)
   - `intent=PROPOSE_PLAN`

4. **降级策略**:
   - 如果LLM调用失败, 使用fallback proposal:
     - `aspect="comprehensive"`
     - `question=原始查询`
     - 3个默认槽位: `core_answer`, `key_points`, `context`

#### Prompt文件

- **位置**: `app/prompts/proposal_decompose_system.md`
- **内容**: 指导LLM生成同结构的slot-filling proposals, 强调这是提取任务而非模板填充

#### 可配置项

- `GENERATION_MAX_PROPOSALS`: 最大proposal数量(默认5)

### 4.2 ContentGenerator — 证据图槽位填空 (Stage 2)

**功能**: 对每个proposal, 从证据图中提取信息填充其定义的槽位.

#### 核心设计理念

**提取 > 生成**: LLM执行的是"从证据中提取信息填入槽位"(提取任务), 而非自由生成.

- **输入**: proposal节点(含slots定义) + 证据图中按`evidence_hint`分类的证据
- **输出**: slot-filled内容节点(`generated_content`)
- **格式**: JSON对象 `{slot_name: {value, confidence, source_evidence_ids}}`

#### 输入输出

- **输入**: 
  - `proposal_nodes` (List[EvidenceNode]): Proposal节点列表
  - `evidence_graph` (EvidenceGraph): 证据图
  - `query` (str): 原始查询
  
- **输出**: 
  - `List[EvidenceNode]`: 生成的内容节点列表
  - `content_type="generated_content"`

#### 处理流程

**对每个Proposal执行提取**

1. **解析Proposal结构**:
   - 从proposal节点的`content`字段解析JSON
   - 提取: `aspect`, `question`, `slots`列表

2. **按hint收集证据**:
   - 根据每个slot的`evidence_hint`收集对应类型的证据节点
   - 映射关系:
     - `fused_evidence` → 标签包含`["fused"]`的节点
     - `kg_match` → 标签包含`["kg_chain", "kg_match"]`的节点
     - `document_chunk` → 标签包含`["vector_result"]`的节点
     - `any` → 所有非proposal类型的节点
   - 过滤: 只保留`confidence >= 0.2`的节点

3. **格式化证据文本**:
   - 按证据类型分组展示
   - 每个证据显示: `[id=xxx conf=0.xx] 内容前250字符`
   - 最多展示8个证据节点

4. **LLM提取填充**:
   - 使用prompt文件 `slot_extraction_system.md`
   - 输入: 
     - 原始查询
     - Proposal的aspect和question
     - Slots定义(JSON格式)
     - 可用证据文本
   - 输出: JSON对象, 格式:
     ```json
     {
       "slot_name": {
         "value": "提取的文本",
         "confidence": 0.85,
         "source_evidence_ids": ["node_id_1", "node_id_2"]
       }
     }
     ```

5. **解析填充结果**:
   - 解析LLM返回的JSON
   - 处理markdown代码块包装
   - 如果解析失败, 创建fallback slot: `{"raw_output": {"value": raw, "confidence": 0.5}}`

6. **构建可读内容**:
   - 将filled slots转换为Markdown格式的可读文本
   - 格式:
     ```markdown
     ## aspect
     
     **Q:** question
     
     **slot_name** (conf=0.xx):
     提取的值
     
     **slot_name**: [insufficient evidence]  (如果value为null)
     ```

7. **计算置信度**:
   - 从所有filled slots的confidence计算平均值
   - 如果所有slots都未填充, 默认confidence=0.3

8. **构建生成节点**:
   - 创建`generated_content`类型节点
   - 元数据包含:
     - `aspect`, `question`
     - `filled_slots`: 完整的filled slots JSON
     - `slot_count`: 总槽位数
     - `filled_count`: 成功填充的槽位数
     - `evidence_count`: 使用的证据节点数
   - `confidence = min(avg_confidence, 1.0)`
   - 通过`DERIVED_FROM`边连接到对应的proposal节点

#### Prompt文件

- **位置**: `app/prompts/slot_extraction_system.md`
- **内容**: 强调从证据中提取, 禁止幻觉, 如果证据不足则设置value为null

#### 关键特性

- **提取优先**: 每个slot必须从提供的证据中提取, 不能凭空生成
- **可追溯性**: 每个filled slot记录`source_evidence_ids`, 可追溯到源证据节点
- **置信度独立**: 每个slot有独立的confidence, 反映证据充分性
- **null处理**: 证据不足的slot值为null, confidence=0

#### 可配置项

- 无独立配置项, 使用全局LLM配置

## 5. 评估Agent功能详细说明 (F-7 ~ F-8)

评估Agent负责**Validate阶段**, 通过重新设计的得分函数, 匈牙利匹配和Auto Prompt优化实现自动化质量评估.

### 5.1 ScoringFunction — 重新设计的得分函数 (F-7)

**功能**: 解决余弦相似度的对称性问题和细粒度识别差的问题.

#### 问题背景

- **余弦相似度对称性**: `cosine(a, b) = cosine(b, a)`, 无法区分查询-文档的方向性
- **细粒度识别差**: 向量检索在细粒度相似度判断上表现不佳

#### 解决方案

**组合得分函数**: `score = α × dense_denoised + (1-α) × sparse`

#### 组件1: 自监督去噪 (Dense Denoised)

**目的**: 去除embedding中的公共噪声方向, 提高信噪比.

**算法流程**:

1. 计算均值向量: `mean_vec = (a + b) / 2`
2. 提取噪声方向: `noise_direction = normalize(mean_vec)`
3. 去噪:
   - `a_denoised = a - λ × dot(a, noise_direction) × noise_direction`
   - `b_denoised = b - λ × dot(b, noise_direction) × noise_direction`
4. 计算去噪后的余弦相似度: `score = cosine(a_denoised, b_denoised)`

**原理**: 两个向量的均值方向代表它们共享的"公共信息", 去除该方向的分量后, 保留的是区分性信息.

**参数**: `λ = denoising_strength` (默认0.1)

#### 组件2: 稀疏矩阵得分 (Sparse, 非对称)

**目的**: 类BM25的非对称词项重叠得分, 打破余弦对称性.

**算法流程**:

1. **Tokenization**: 对query和document分别进行分词
2. **TF计算**: 在document中计算term frequency
3. **IDF计算**: 从query角度计算inverse document frequency (查询词越独特, 权重越高)
4. **TF归一化**: 使用BM25公式:
   ```
   score = Σ IDF(q_i) × (TF(q_i, d) × (k1 + 1)) / (TF(q_i, d) + k1 × (1 - b + b × |d|/avgdl))
   ```
   - `k1 = 1.2` (BM25标准参数)
   - `b = 0.75` (长度归一化参数)

**关键特性**: `score(query, doc) ≠ score(doc, query)`, 因为IDF是从第一个参数(query)角度计算的, 这打破了余弦相似度的对称性.

#### 组合公式

```
combined_score = α × dense_denoised + (1-α) × sparse
```

- `α = 1 - EVALUATION_SPARSE_WEIGHT` (默认0.7, 即sparse权重0.3)
- `dense_denoised`: 去噪后的余弦相似度 (0.0~1.0)
- `sparse`: BM25-like稀疏得分 (归一化到0.0~1.0)

#### 批量计算

- `batch_score(predictions, targets)`: 计算预测-目标对的得分矩阵
- 返回: `numpy.ndarray` 形状 `(n_predictions × n_targets)`

#### 可配置项

- `EVALUATION_SPARSE_WEIGHT`: 稀疏得分权重(默认0.3)
- `denoising_strength`: 去噪强度(默认0.1)

### 5.2 HungarianMatcher — 匈牙利匹配评估 (F-7)

**功能**: 使用scipy.optimize.linear_sum_assignment实现section-evidence二部图最优匹配.

#### 设计灵感

**类比**: DETR (DEtection TRansformer) 的二部图匹配机制.

- **DETR**: 预测框 ↔ 真实框的匹配
- **本系统**: 生成内容section ↔ 证据源的匹配

#### 输入输出

- **输入**: 
  - `predictions` (List[Dict]): 生成内容列表, 每个包含 `embedding`, `tokens`, `content`, `id`
  - `targets` (List[Dict]): 证据源列表, 每个包含 `embedding`, `tokens`, `content`, `id`
  
- **输出**: 
  - `Dict` 包含:
    - `matches`: `[(pred_idx, target_idx, score)]` 匹配对列表
    - `unmatched_preds`: 未匹配的预测索引列表
    - `unmatched_targets`: 未匹配的目标索引列表
    - `cost_matrix`: 完整的代价矩阵
    - `overall_score`: 加权平均匹配质量

#### 处理流程

1. **计算得分矩阵**:
   - 使用`ScoringFunction.batch_score(predictions, targets)`
   - 得到相似度矩阵 `S[i,j]` (形状: `n_predictions × n_targets`)

2. **转换为代价矩阵**:
   - `C = 1.0 - S` (匈牙利算法最小化代价, 而我们需要最大化相似度)

3. **求解最优匹配**:
   - 调用 `scipy.optimize.linear_sum_assignment(C)`
   - 返回: `(row_indices, col_indices)` 最优匹配索引对

4. **评估匹配质量**:
   - 对每个匹配对 `(i, j)`:
     - `match_score = S[i, j]`
     - `is_faithful = match_score >= threshold` (默认threshold=0.5)
   - 汇总:
     - `faithfulness_rate = faithful_count / total_matches`
     - `overall_score = mean(match_scores)`

5. **识别未匹配项**:
   - `unmatched_preds`: 所有预测索引 - 已匹配的预测索引
   - `unmatched_targets`: 所有目标索引 - 已匹配的目标索引

#### 边界情况处理

- **空输入**: 如果`n_pred == 0` 或 `n_targ == 0`, 返回空匹配结果
- **非方阵**: `linear_sum_assignment`支持矩形矩阵, 自动处理

#### 可配置项

- `faithfulness_threshold`: 忠实度阈值(默认0.5)

### 5.3 AutoPromptOptimizer — Auto Prompt优化 (F-8)

**功能**: 基于评估结果诊断弱section, 生成prompt补丁, 实现持续自我改进.

#### 触发条件

- `overall_score < EVALUATION_CONFIDENCE_THRESHOLD` (默认阈值可配置)

#### 输入输出

- **输入**: 
  - `evaluation_results` (Dict): HungarianMatcher的输出结果
  - `evidence_graph` (EvidenceGraph): 当前证据图
  - `current_prompts` (Optional[Dict[str, str]]): 当前prompt模板(可选)
  
- **输出**: 
  - `List[EvidenceNode]`: Prompt优化建议节点列表
  - `content_type="prompt_optimization"`

#### 处理流程

**阶段1: 识别弱Section**

1. **从评估结果提取弱section**:
   - `score < 0.5` 的匹配对
   - `is_faithful = False` 的匹配对
   - 未匹配的生成section (`unmatched_sections`)

2. **构建弱section列表**:
   ```python
   weak_sections = [
       {
           "section_idx": idx,
           "score": score,
           "is_faithful": False,
           "issue": "low_score" | "unmatched"
       }
   ]
   ```

**阶段2: LLM诊断与生成补丁**

3. **调用LLM生成优化建议**:
   - 使用prompt文件 `auto_prompt_system.md`
   - 输入:
     - 弱section列表(JSON格式)
     - 当前prompt模板(截断到200字符, 避免上下文过长)
   - 输出: JSON数组, 每个元素包含:
     ```json
     {
       "diagnosis": "问题诊断描述",
       "target": "优化目标(prompt名称)",
       "prompt_patch": "具体的prompt修改建议",
       "expected_improvement": 0.0-1.0
     }
     ```

4. **解析优化建议**:
   - 处理markdown代码块包装
   - 如果解析失败, 创建fallback建议

**阶段3: 构建优化节点**

5. **创建优化建议节点**:
   - 每个优化建议创建`prompt_optimization`类型节点
   - 元数据包含: `diagnosis`, `target`, `expected_improvement`
   - `confidence = expected_improvement`
   - `intent = OPTIMIZE_PROMPT`
   - 标签: `["prompt_optimization", target]`

#### Prompt文件

- **位置**: `app/prompts/auto_prompt_system.md`
- **功能**: 指导LLM分析弱section, 诊断问题(幻觉/缺上下文/粒度错误), 生成针对性的prompt补丁

#### 优化目标类型

- `system_prompt`: 系统级prompt优化
- `proposal_template`: Proposal生成模板优化
- `extraction_template`: 槽位提取模板优化

#### 可配置项

- `EVALUATION_CONFIDENCE_THRESHOLD`: 触发优化的置信度阈值

## 6. HITL人工审核功能 (F-9)

**功能**: 在评估完成后, 如果质量处于边界区间, Gateway路由到human_review节点, 等待人工审核.

### 6.1 触发机制

- **路由决策**: Gateway节点根据评估结果决定是否进入人工审核
- **条件**: 质量分数在边界区间(可配置), 或用户明确请求审核

### 6.2 实现机制

**LangGraph interrupt_before机制**:

- 在`human_review`节点前设置`interrupt_before`
- 管道暂停, 等待人工输入
- 状态保存在PostgreSQL checkpoint中

### 6.3 人工操作选项

| 操作 | 效果 | 后续流程 |
|------|------|---------|
| `approve` | 确认通过 | 进入输出组装 (`assemble_output`) |
| `reject` | 打回重新生成 | 附带反馈文本, 进入Rollback阶段 |
| `edit` | 直接修改证据图内容 | 修改后继续流程 |

### 6.4 API接口

- **提交审核**: `POST /api/v1/agent/human-review/{session_id}`
- **请求体**:
  ```json
  {
    "action": "approve" | "reject" | "edit",
    "feedback": "反馈文本(可选)",
    "edited_content": "编辑后的内容(edit时必需)"
  }
  ```

### 6.5 可配置项

- `HITL_ENABLED`: 是否启用人工审核(默认true)
- `HITL_THRESHOLD_LOW`: 触发审核的低阈值
- `HITL_THRESHOLD_HIGH`: 触发审核的高阈值

### 6.6 API表现层并发(线程池)

- 实现位置: `app/presentation/api/v1/agent.py`
- 设计原则:
  - Agent编排保持串行状态机执行(Explore -> Freeze -> Plan -> Execute -> Validate -> Done/Rollback)。
  - 线程池仅用于表现层响应组装(如中间产物分组、状态序列化、summary构建)。
- 目的:
  - 提升API层在高并发请求下的响应组装吞吐, 避免阻塞主事件循环。
- 可配置项:
  - `API_PRESENTATION_MAX_WORKERS`: 表现层线程池并发度(默认4)。

所有prompt模板以Markdown文件形式管理, 便于版本控制和协作.

### 8.1 Prompt文件列表

| 文件名 | 用途 | 使用位置 |
|-------|------|---------|
| `query_decompose_system.md` | Query分解系统prompt | `QueryDecomposer._llm_decompose()` |

### 8.2 Prompt加载机制

**函数**: `app.prompts.load_prompt(prompt_name: str, **kwargs) -> str`

**功能**:
- 从`app/prompts/`目录加载Markdown文件
- 支持模板变量替换(通过`**kwargs`)
- 缓存已加载的prompt内容

**示例**:
```python
prompt = load_prompt(
    "query_decompose_system",
    max_sub_queries=5
)
```

### 8.3 Prompt文件格式

- **文件扩展名**: `.md`
- **编码**: UTF-8
- **内容**: 纯文本Markdown, 支持变量占位符 `{variable_name}`

### 8.4 优势

- **版本控制**: 所有prompt变更通过Git追踪
- **协作友好**: Markdown格式便于阅读和编辑
- **集中管理**: 所有prompt集中在一个目录
- **易于测试**: 可以独立测试prompt效果

## 10. 总结

本系统通过管理式金字塔架构分层和LangGraph状态机编排, 实现了从查询到高质量结构化回答的完整流程. 核心创新包括:

6. **Auto Prompt优化**: 基于评估反馈的持续自我改进

所有功能均已实现并通过测试, 系统已具备生产级部署能力.
