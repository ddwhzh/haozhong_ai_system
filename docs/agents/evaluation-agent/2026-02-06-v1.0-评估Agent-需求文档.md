## 1. 背景与问题陈述

### 1.1 业务背景

在AI生成内容的评估场景中, 传统方法存在以下核心问题:

1. **对称性问题 (Symmetry Problem)**
   - 余弦相似度 `cos(A, B) = cos(B, A)` 是对称的
   - 但相关性评估本质上是非对称的: 生成内容对证据的匹配度 ≠ 证据对生成内容的匹配度
   - 例如: 一段简短证据可能完全匹配长文本的某个片段, 但反向匹配度较低

2. **细粒度相似度判别能力不足 (Fine-grained Similarity Discrimination)**
   - 向量检索在细粒度匹配上表现不佳
   - 相似但不同的内容往往获得几乎相同的嵌入分数
   - 难以区分"部分匹配"和"完全匹配"的情况

3. **手动提示词工程瓶颈 (Manual Prompt Engineering Bottleneck)**
   - 传统方法需要人工分析评估结果并手动优化提示词
   - 缺乏自动化的反馈循环来持续改进生成质量
   - 无法系统性地识别和修复弱项

### 1.2 技术挑战

- **P5问题**: 对称性和细粒度相似度问题 (Symmetry and Fine-grained Similarity Problem)
- **评估自动化**: 需要自动化的、基于分配的质量评估机制, 而非简单的聚合分数
- **持续改进**: 需要基于评估反馈的自动提示词优化能力

## 2. 需求概述

### 2.1 功能需求

#### FR-1: 混合评分函数 (Hybrid Scoring Function)
- **描述**: 实现结合密集向量和稀疏矩阵的混合评分机制
- **要求**:
  - 支持自监督去噪的密集向量评分
  - 支持BM25风格的稀疏词项重叠评分
  - 可配置的混合权重: `hybrid_score = alpha * embedding_score + (1-alpha) * sparse_score`
  - 解决对称性问题: `score(query, doc) ≠ score(doc, query)`

#### FR-2: 匈牙利匹配算法 (Hungarian Matching)
- **描述**: 实现基于匈牙利算法的二部图最优匹配
- **要求**:
  - 将生成内容片段与证据源进行最优匹配
  - 使用 `scipy.optimize.linear_sum_assignment` 进行成本矩阵优化
  - 支持非对称匹配 (生成内容 ↔ 证据)
  - 输出匹配对、未匹配项和整体评分

#### FR-3: 忠实度评估 (Faithfulness Evaluation)
- **描述**: 基于匈牙利匹配结果评估生成内容的忠实度
- **要求**:
  - 计算忠实度率: 匹配对中分数 ≥ 阈值的比例
  - 计算完整性率: 参考项中被匹配的比例
  - 为每个生成片段提供独立的评分和忠实度标记
  - 支持可配置的置信度阈值 (`EVALUATION_CONFIDENCE_THRESHOLD`)

#### FR-4: 自动提示词优化 (Auto Prompt Optimization)
- **描述**: 基于评估结果自动生成提示词改进建议
- **要求**:
  - 识别弱项片段: 低匹配分数、不忠实内容、未匹配项
  - 诊断问题: 缺失上下文、错误粒度、幻觉等
  - 生成提示词补丁: 针对系统提示词/模板的具体修改建议
  - 仅在整体评分低于阈值时触发

#### FR-5: 证据图集成 (Evidence Graph Integration)
- **描述**: 与证据图系统集成, 支持评估结果和提示词优化的持久化
- **要求**:
  - 创建 `evaluation_result` 类型的证据节点
  - 创建 `prompt_optimization` 类型的证据节点
  - 更新生成内容节点的信念置信度
  - 支持评估结果的可追溯性

### 2.2 非功能需求

#### NFR-1: 性能要求
- 评分计算延迟: < 100ms (单次匹配)
- 批量评分延迟: < 1s (100个片段)
- 匈牙利匹配延迟: < 500ms (100x100矩阵)

#### NFR-2: 可扩展性
- 支持最多1000个生成片段和1000个证据源的匹配
- 支持异步处理以提高吞吐量

#### NFR-3: 可配置性
- 稀疏权重可配置 (`EVALUATION_SPARSE_WEIGHT`, 默认0.3)
- 置信度阈值可配置 (`EVALUATION_CONFIDENCE_THRESHOLD`, 默认0.7)
- 去噪强度可配置 (默认0.1)

#### NFR-4: 可观测性
- 记录所有评估操作的详细日志
- 输出评估指标: 整体评分、忠实度率、片段数量、信念更新数量
- 支持Langfuse追踪LLM调用

## 4. 验收标准

### AC-1: 评分函数正确性
- [ ] 混合评分函数能够正确计算密集和稀疏分数
- [ ] 稀疏评分能够打破对称性 (验证 `score(A, B) ≠ score(B, A)`)
- [ ] 去噪机制能够提高信号噪声比

### AC-2: 匈牙利匹配正确性
- [ ] 匹配算法能够找到最优分配
- [ ] 匹配结果满足一对一约束 (每个生成片段最多匹配一个证据源)
- [ ] 成本矩阵计算正确 (成本 = 1 - 相似度分数)

### AC-3: 忠实度评估准确性
- [ ] 忠实度率计算正确 (匹配对中分数 ≥ 阈值的比例)
- [ ] 完整性率计算正确 (参考项中被匹配的比例)
- [ ] 每个片段都有正确的忠实度标记

### AC-4: 自动提示词优化有效性
- [ ] 能够正确识别弱项片段 (分数 < 阈值或未匹配)
- [ ] 能够生成结构化的提示词优化建议
- [ ] 优化建议包含诊断、补丁、预期改进等信息

### AC-5: 集成测试
- [ ] 评估Agent能够正确处理空输入 (无生成内容)
- [ ] 评估结果能够正确更新证据图
- [ ] 信念更新能够正确传播到生成内容节点

## 5. 约束条件

### C-1: 技术约束
- 必须使用 `scipy.optimize.linear_sum_assignment` 进行匈牙利匹配
- 必须支持异步操作 (async/await)
- 必须遵循项目的日志规范 (structlog, 小写下划线格式)

### C-2: 架构约束
- 必须继承 `BaseAgent` 基类
- 必须使用 `EvidenceGraph` 进行数据管理
- 必须使用 `Belief` 和 `BeliefUpdate` 进行信念管理

### C-3: 配置约束
- 所有配置项必须通过环境变量或 `settings` 对象访问
- 默认值必须合理且经过测试验证

## 7. 风险与缓解措施

### R-1: 评分函数性能问题
- **风险**: 大规模匹配时计算延迟过高
- **缓解**: 使用批量计算和异步处理, 优化矩阵运算

### R-2: 匈牙利匹配内存占用
- **风险**: 大规模矩阵可能导致内存溢出
- **缓解**: 限制单次匹配的最大规模, 使用分批处理

### R-3: 自动提示词优化质量不稳定
- **风险**: LLM生成的优化建议可能不准确
- **缓解**: 添加验证机制, 支持人工审核, 记录优化历史

## 9. 术语表

- **匈牙利匹配 (Hungarian Matching)**: 一种解决二部图最优分配问题的算法, 源自DETR (DEtection TRansformer)
- **忠实度率 (Faithfulness Rate)**: 匹配对中分数达到阈值的比例
- **完整性率 (Completeness Rate)**: 参考项中被成功匹配的比例
- **稀疏评分 (Sparse Score)**: 基于词项重叠的BM25风格评分
- **密集评分 (Dense Score)**: 基于向量嵌入的余弦相似度评分
- **去噪 (Denoising)**: 通过移除噪声分量来提高嵌入质量的技术
- **提示词补丁 (Prompt Patch)**: 对现有提示词的增量修改建议
