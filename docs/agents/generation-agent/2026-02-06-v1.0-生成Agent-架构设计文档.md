## 1. 概述

### 1.1 设计目标

生成Agent采用**Proposal-based Slot-filling机制**, 受Fast RCNN两阶段检测架构启发, 通过以下设计实现粒度一致的内容生成:

1. **两阶段Pipeline**: Proposal分解 → Slot提取
2. **结构化Proposal**: 定义slots而非模板, 确保结构一致性
3. **证据图提取**: 从EvidenceGraph中提取信息填充slots, 而非自由生成

### 1.2 核心设计理念

- **Extraction > Generation**: 优先从证据中提取, 而非自由生成
- **Structure Consistency**: 所有proposal共享相同结构, 保证粒度一致
- **Traceability**: 每个filled slot都链接回源证据节点

## 3. 数据流设计

### 3.1 完整数据流

```
1. Input: AgentInput
   ├── query: str
   └── evidence_graph: EvidenceGraph

2. Stage 1: Proposal Decomposition
   ├── Input: query + evidence_graph
   ├── Process:
   │   ├── 提取高置信度节点 (confidence >= 0.3)
   │   ├── 汇总证据信息
   │   ├── 统计证据类型
   │   └── LLM生成N个proposal
   └── Output: List[EvidenceNode] (proposal类型)

3. Stage 2: Slot Extraction
   ├── Input: proposal_nodes + evidence_graph + query
   ├── Process:
   │   ├── 对每个proposal:
   │   │   ├── 解析proposal的slots定义
   │   │   ├── 根据evidence_hint匹配证据节点
   │   │   ├── LLM提取信息填充slots
   │   │   └── 生成readable content
   │   └── 按priority排序
   └── Output: List[EvidenceNode] (generated_content类型)

4. Output Assembly
   ├── Input: generated_nodes
   ├── Process:
   │   ├── 提取每个节点的content
   │   └── 用分隔符连接
   └── Output: str (最终文本)

5. Final Output: AgentOutput
   ├── status: AgentStatus
   ├── new_nodes: proposal_nodes + generated_nodes
   ├── summary: str
   └── metrics: dict
```

### 3.2 证据图更新流程

```
初始EvidenceGraph (来自Retrieval Agent)
    │
    ├─▶ Proposal Decomposition
    │       │
    │       └─▶ 添加Proposal Nodes
    │           ├── content_type: "proposal"
    │           ├── metadata: {aspect, question, slot_count, priority, index}
    │           └── intent: IntentType.PROPOSE_PLAN
    │
    └─▶ Slot Extraction
            │
            └─▶ 添加Generated Content Nodes
                ├── content_type: "generated_content"
                ├── metadata: {aspect, question, filled_slots, slot_count, filled_count}
                └── intent: IntentType.GENERATE
                └── parent_node_ids: [proposal_node_id]
```

## 4. Proposal结构设计

### 4.1 Proposal JSON结构

```json
{
  "aspect": "定义",
  "question": "什么是X?",
  "slots": [
    {
      "name": "core_definition",
      "description": "核心定义",
      "evidence_hint": "fused_evidence"
    },
    {
      "name": "key_characteristics",
      "description": "关键特征",
      "evidence_hint": "kg_match"
    },
    {
      "name": "examples",
      "description": "示例",
      "evidence_hint": "document_chunk"
    }
  ],
  "priority": 1
}
```

### 4.2 Proposal字段说明

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| aspect | string | 是 | 要处理的方面, 如"定义"、"组件"、"应用"等 |
| question | string | 是 | 该方面的具体问题 |
| slots | array | 是 | 需要填充的信息槽位列表 |
| priority | integer | 是 | 优先级, 1-5, 1为最高 |

### 4.3 Slot结构说明

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| name | string | 是 | Slot名称, 用于标识 |
| description | string | 是 | Slot描述, 说明需要提取什么信息 |
| evidence_hint | string | 是 | 证据类型提示, 用于匹配证据节点 |

### 4.4 Evidence Hint类型

| Hint值 | 匹配规则 | 说明 |
|--------|---------|------|
| fused_evidence | tags包含"fused" | 融合后的证据 |
| kg_match | tags包含"kg_chain"或"kg_match" | 知识图谱匹配结果 |
| document_chunk | tags包含"vector_result" | 向量检索的文档片段 |
| any | 排除proposal类型, confidence >= 0.2 | 任意类型证据 |

### 4.5 Proposal Node元数据

```python
{
    "aspect": "定义",
    "question": "什么是X?",
    "slot_count": 3,
    "priority": 1,
    "index": 0
}
```

## 5. Slot-filling机制设计

### 5.1 Slot提取流程

```
1. 解析Proposal
   └─▶ 提取aspect、question、slots

2. 根据Evidence Hint匹配证据节点
   ├─▶ 遍历所有slots
   ├─▶ 对每个slot的evidence_hint:
   │   ├─▶ 查找匹配的tags
   │   └─▶ 过滤confidence >= 0.2的节点
   └─▶ 组织为evidence_by_hint字典

3. 格式化证据供LLM提取
   └─▶ 按hint分组, 每个hint最多8个节点

4. LLM提取
   ├─▶ 输入: proposal + evidence
   ├─▶ 输出: filled_slots JSON
   └─▶ 格式: {slot_name: {value, confidence, source_evidence_ids}}

5. 生成Readable Content
   └─▶ 将filled_slots转换为可读文本
```

### 5.2 Filled Slot结构

```json
{
  "core_definition": {
    "value": "X是...",
    "confidence": 0.9,
    "source_evidence_ids": ["node_id_1", "node_id_2"]
  },
  "key_characteristics": {
    "value": null,
    "confidence": 0.0,
    "source_evidence_ids": []
  }
}
```

### 5.3 Generated Content Node元数据

```python
{
    "aspect": "定义",
    "question": "什么是X?",
    "filled_slots": {...},  # 完整的filled_slots JSON
    "slot_count": 3,
    "filled_count": 2,  # 成功填充的slot数量
    "evidence_count": 5  # 使用的证据节点总数
}
```

## 6. 模块设计

### 6.1 GenerationAgent (agent.py)

**职责**: 两阶段Pipeline的协调者

**主要方法**:
- `_execute(agent_input)`: 执行两阶段流程
- `_assemble_output(generated_nodes)`: 组装最终输出

**关键逻辑**:
1. 调用ProposalDecomposer生成proposal节点
2. 调用ContentGenerator填充slots
3. 组装最终输出文本
4. 返回AgentOutput

### 6.2 ProposalDecomposer (proposal_decomposer.py)

**职责**: Stage 1 - 将查询分解为N个相同结构的proposal

**主要方法**:
- `generate_proposals(query, evidence_graph)`: 生成proposal节点列表
- `_summarize_evidence(nodes)`: 汇总证据信息
- `_count_evidence_types(evidence_graph)`: 统计证据类型
- `_llm_propose(...)`: LLM生成proposal
- `_fallback_proposal(query)`: 生成fallback proposal

**关键逻辑**:
1. 提取高置信度节点 (threshold=0.3)
2. 汇总证据信息和统计
3. 调用LLM生成proposal JSON数组
4. 将每个proposal转换为EvidenceNode
5. 错误处理: 使用fallback proposal

### 6.3 ContentGenerator (content_generator.py)

**职责**: Stage 2 - 从证据图中提取信息填充proposal的slots

**主要方法**:
- `generate(proposal_nodes, evidence_graph, query)`: 批量处理proposal
- `_extract_for_proposal(...)`: 处理单个proposal
- `_gather_evidence_by_hint(...)`: 根据hint匹配证据节点
- `_format_evidence_for_extraction(...)`: 格式化证据供LLM使用
- `_parse_filled_slots(raw)`: 解析LLM输出的filled slots
- `_slots_to_readable(...)`: 将filled slots转换为可读文本

**关键逻辑**:
1. 按priority排序proposal
2. 对每个proposal:
   - 解析proposal JSON
   - 根据evidence_hint匹配证据节点
   - 调用LLM提取信息填充slots
   - 生成readable content
   - 创建Generated Content Node
3. 错误处理: 跳过失败的proposal, 继续处理其他

## 8. 错误处理设计

### 8.1 Proposal生成失败

**场景**: LLM调用失败或返回无效JSON

**处理策略**:
1. 捕获异常, 记录错误日志
2. 使用`_fallback_proposal(query)`生成默认proposal
3. 继续执行后续流程

**Fallback Proposal结构**:
```json
{
  "aspect": "comprehensive",
  "question": "<原始查询>",
  "slots": [
    {"name": "core_answer", "description": "Direct answer", "evidence_hint": "fused_evidence"},
    {"name": "key_points", "description": "2-3 key points", "evidence_hint": "fused_evidence"},
    {"name": "context", "description": "Background info", "evidence_hint": "document_chunk"}
  ],
  "priority": 1
}
```

### 8.2 Slot提取失败

**场景**: 单个proposal的slot提取失败

**处理策略**:
1. 捕获异常, 记录错误日志 (包含proposal aspect)
2. 跳过该proposal, 继续处理其他proposal
3. 最终状态: 如果至少1个proposal成功, 返回SUCCESS; 否则返回PARTIAL

### 8.3 无Proposal生成

**场景**: ProposalDecomposer返回空列表

**处理策略**:
1. 检查proposal_nodes是否为空
2. 如果为空, 返回ERROR状态
3. error_message: "No proposals generated"

## 9. 性能优化设计

### 9.1 并行化机会

**当前设计**: 串行处理每个proposal的slot提取

**优化方向**: 可以并行处理多个proposal的slot提取 (未来优化)

### 9.2 证据节点过滤

**优化点**: 
- 只使用高置信度节点 (confidence >= 0.3) 进行proposal生成
- 只使用confidence >= 0.2的节点进行slot提取
- 每个hint类型最多使用8个节点

### 9.3 缓存策略

**潜在优化**: 
- 缓存证据汇总结果 (如果evidence_graph未变化)
- 缓存proposal结构 (如果查询相似)

## 10. 可观测性设计

### 10.1 日志记录

**关键日志点**:
- `generation_pipeline_start`: Pipeline开始
- `proposals_generated`: Proposal生成完成, 记录数量和aspect列表
- `slot_extraction_failed`: Slot提取失败, 记录proposal aspect和错误
- `slot_extraction_complete`: Slot提取完成, 记录成功数量
- `generation_pipeline_complete`: Pipeline完成, 记录proposal数量、生成数量、状态

### 10.2 指标收集

**AgentOutput.metrics包含**:
- `proposal_count`: Proposal数量
- `generated_count`: 成功生成的内容数量
- `final_output_length`: 最终输出文本长度
- `elapsed_seconds`: 总耗时

**Generated Content Node元数据包含**:
- `slot_count`: Slot总数
- `filled_count`: 成功填充的slot数量
- `evidence_count`: 使用的证据节点数量

### 10.3 Langfuse追踪

**追踪点**:
- Proposal分解的LLM调用
- 每个proposal的Slot提取LLM调用

## 11. 与Fast RCNN的类比

| Fast RCNN | Generation Agent |
|-----------|----------------|
| RPN (Region Proposal Network) | ProposalDecomposer |
| ROI Head | ContentGenerator |
| Region Proposals | Proposals |
| Object Detection | Slot Extraction |
| Bounding Boxes | Filled Slots |
| Feature Map | Evidence Graph |

**核心思想**: 
- Fast RCNN先提出候选区域, 再对每个区域进行分类和定位
- Generation Agent先提出proposal, 再对每个proposal进行slot提取和填充

## 12. 扩展性设计

### 12.1 新增Evidence Hint类型

**扩展方式**:
1. 在`ContentGenerator._gather_evidence_by_hint()`中添加新的hint到tags映射
2. 更新提示词说明新的hint类型

### 12.2 自定义Slot结构

**扩展方式**:
1. 修改Proposal JSON结构, 添加slot的额外字段
2. 更新`ContentGenerator._parse_filled_slots()`解析逻辑

### 12.3 多语言支持

**扩展方式**:
1. 根据query语言选择对应的提示词模板
2. 保持Proposal和Slot的JSON结构不变
