## 1. 背景与问题

### 1.1 问题背景 (P4问题)

在传统的LLM自由生成模式下, 系统面临一个关键问题: **生成各项结果的粒度不一致**。

#### 问题表现

- **详略程度差异巨大**: 在生成报告、回答等结构化内容时, 不同部分的详略程度差异巨大。例如生成报告时, 某些章节500字, 某些章节仅50字, 缺乏统一的结构化约束。
- **输出质量不可控**: LLM自由生成模式下, 无法保证各部分内容的完整性和一致性。
- **用户体验差**: 用户期望获得结构统一、粒度一致的回答, 但实际输出往往参差不齐。
- **难以进行自动化评估**: 由于输出粒度不一致, 难以建立统一的评估标准, 影响系统优化。

#### 实际案例

某系统生成的报告共10个章节, 其中:
- 3个章节内容完整 (800+字)
- 5个章节仅标题 (20字)
- 2个章节缺失

这种不一致性严重影响了系统的可用性和专业性。

### 1.2 现有方案的局限性

#### 方案1: 自由生成模式
- **优点**: 灵活性高, 适应性强
- **缺点**: 粒度不一致, 质量不可控

#### 方案2: 模板化方案
- **优点**: 结构统一, 粒度一致
- **缺点**: 过于僵化, 无法适应动态内容需求, 缺乏灵活性

### 1.3 创新方案: Proposal-based Slot-filling

受Fast RCNN启发, 我们提出了一种**Proposal-based Slot-filling机制**:

- **Proposal分解**: 将生成任务分解为N个相同结构的proposal, 每个proposal定义需要填充的slots
- **Slot提取**: 从证据图中提取信息填充每个proposal的slots
- **结构化输出**: 所有proposal共享相同结构, 确保粒度一致性

这种方案既保证了结构统一性, 又保持了内容的动态适应性。

## 2. 功能需求

### 2.1 核心功能

#### FR-1: Proposal分解功能

**需求描述**: 系统应能够将用户查询分解为N个相同结构的proposal, 每个proposal定义需要填充的信息slots。

**详细要求**:
- 输入: 用户查询 + 证据图
- 输出: N个相同结构的proposal (N ≤ GENERATION_MAX_PROPOSALS, 默认5)
- 每个proposal包含:
  - `aspect`: 要处理的方面 (如: 定义、组件、应用)
  - `question`: 该方面的具体问题
  - `slots`: 需要填充的信息槽位列表
  - `priority`: 优先级 (1-5, 1为最高)

**约束条件**:
- 所有proposal必须共享相同的slot结构
- Proposal数量不超过配置的最大值 (默认5)
- 每个proposal必须至少包含1个slot

#### FR-2: Slot提取功能

**需求描述**: 系统应能够从证据图中提取信息, 填充每个proposal定义的slots。

**详细要求**:
- 输入: Proposal节点 + 证据图 + 用户查询
- 输出: 填充完成的生成内容节点
- 每个slot包含:
  - `name`: slot名称
  - `description`: slot描述
  - `evidence_hint`: 证据类型提示 (如: fused_evidence, kg_match, document_chunk)
- 提取规则:
  - 根据`evidence_hint`匹配证据图中的节点
  - 从匹配的节点中提取相关信息
  - 如果证据不足, slot值设为null, confidence设为0

**约束条件**:
- 只能从证据图中提取信息, 不能虚构内容
- 每个slot必须标注confidence和source_evidence_ids
- 如果所有slots都无法填充, 返回PARTIAL状态

#### FR-3: 内容组装功能

**需求描述**: 系统应能够将多个填充完成的proposal组装成最终输出文本。

**详细要求**:
- 输入: 多个生成内容节点
- 输出: 格式化的最终文本
- 组装规则:
  - 按priority排序 (priority越小越靠前)
  - 每个proposal的内容用分隔符分隔 (`\n\n---\n\n`)
  - 保留aspect和question信息

### 2.2 非功能需求

#### NFR-1: 性能要求

- Proposal分解阶段: 单次LLM调用, 响应时间 < 10秒
- Slot提取阶段: 每个proposal独立处理, 可并行化, 单个proposal处理时间 < 15秒
- 总体响应时间: 5个proposal情况下 < 90秒

#### NFR-2: 可靠性要求

- Proposal生成失败时, 使用fallback proposal
- Slot提取失败时, 跳过该proposal, 继续处理其他proposal
- 至少保证1个proposal成功生成, 否则返回ERROR状态

#### NFR-3: 可配置性要求

- `GENERATION_MAX_PROPOSALS`: 最大proposal数量 (默认5)
- `GENERATION_PROPOSAL_TEMPERATURE`: Proposal生成温度 (默认0.3)

#### NFR-4: 可观测性要求

- 记录proposal生成数量、aspect列表
- 记录每个proposal的slot填充情况 (filled_count / slot_count)
- 记录总体处理时间和各阶段耗时
- 记录错误信息和失败原因

## 3. 验收标准

### 3.1 功能验收标准

#### AC-1: Proposal分解验收

- [ ] 能够成功将查询分解为1-5个proposal
- [ ] 所有proposal共享相同的slot结构
- [ ] 每个proposal包含aspect、question、slots、priority字段
- [ ] Proposal数量不超过GENERATION_MAX_PROPOSALS配置值

#### AC-2: Slot提取验收

- [ ] 能够成功从证据图中提取信息填充slots
- [ ] 每个filled slot包含value、confidence、source_evidence_ids
- [ ] 证据不足时, slot值正确设为null, confidence设为0
- [ ] 不虚构任何信息, 所有内容均来自证据图

#### AC-3: 内容组装验收

- [ ] 能够正确组装多个proposal的内容
- [ ] 输出格式正确, 包含aspect和question信息
- [ ] Proposal按priority正确排序

### 3.2 质量验收标准

#### AC-4: 粒度一致性验收

- [ ] 所有proposal的输出长度差异 < 50% (相对平均值)
- [ ] 所有proposal的slot数量相同
- [ ] 所有proposal的filled_count差异 < 2个slot

#### AC-5: 内容质量验收

- [ ] 生成内容与证据图高度相关 (相关性 > 0.8)
- [ ] 生成内容不包含明显的虚构信息
- [ ] 生成内容结构清晰, 可读性强

### 3.3 性能验收标准

#### AC-6: 性能验收

- [ ] Proposal分解阶段响应时间 < 10秒
- [ ] 单个proposal的slot提取时间 < 15秒
- [ ] 5个proposal总体处理时间 < 90秒

### 3.4 可靠性验收标准

#### AC-7: 错误处理验收

- [ ] Proposal生成失败时, 能够使用fallback proposal继续处理
- [ ] Slot提取失败时, 能够跳过该proposal, 继续处理其他proposal
- [ ] 至少保证1个proposal成功生成, 否则正确返回ERROR状态

## 4. 约束条件

### 4.1 技术约束

- 必须使用LangGraph进行状态管理
- 必须使用EvidenceGraph进行证据管理
- 必须使用structlog进行日志记录
- 必须使用Langfuse进行LLM调用追踪

### 4.2 架构约束

- 必须遵循BaseAgent接口规范
- 必须使用AgentInput和AgentOutput进行输入输出
- 必须返回AgentStatus状态

### 4.3 数据约束

- Proposal必须存储为EvidenceNode, content_type为"proposal"
- 生成内容必须存储为EvidenceNode, content_type为"generated_content"
- 所有节点必须包含Belief和Intent信息

## 5. 依赖关系

### 5.1 上游依赖

- **Retrieval Agent**: 提供证据图 (EvidenceGraph)
- **Planning Agent**: 确定是否需要生成阶段

### 5.2 下游依赖

- **Evaluation Agent**: 评估生成内容质量
- **Presentation Layer**: 展示最终结果给用户

### 5.3 基础设施依赖

- LLM服务 (llm_service)
- 提示词管理 (prompts)
- 配置管理 (settings)
- 日志服务 (logger)

## 6. 术语表

| 术语 | 英文 | 定义 |
|------|------|------|
| Proposal | Proposal | 定义了需要填充的信息slots的结构化任务 |
| Slot | Slot | 需要从证据图中提取的信息单元, 包含name、description、evidence_hint |
| Aspect | Aspect | Proposal要处理的方面, 如定义、组件、应用等 |
| Evidence Hint | Evidence Hint | Slot匹配证据类型的提示, 如fused_evidence、kg_match、document_chunk |
| Evidence Graph | Evidence Graph | 包含所有检索到的证据节点的图结构 |
| Slot-filling | Slot-filling | 从证据图中提取信息填充proposal定义的slots的过程 |
| Proposal Decomposer | Proposal Decomposer | 负责将查询分解为proposal的模块 |
| Content Generator | Content Generator | 负责从证据图中提取信息填充slots的模块 |
