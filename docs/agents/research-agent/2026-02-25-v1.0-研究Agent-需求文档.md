## 1. 背景与问题

### 1.1 问题背景 (P4问题)

在传统的LLM辅助研究中, 系统面临一个根本瓶颈: **研究过程是单轮的, 缺乏闭环反馈与迭代修正能力**.

#### 问题表现

- **一次性回答**: 用户提问后获得一次性回答, 无法基于实验证据进行假设修正.
- **文献检索孤立**: 文献检索与实验验证之间没有反馈通路, 检索策略无法根据实验结果动态调整.
- **实验不可验证**: LLM生成的"实验结果"往往是幻觉, 缺乏真实的代码执行和量化指标.
- **无收敛保证**: 没有迭代限制和决策机制, 研究过程可能发散或陷入死循环.

#### 实际案例

某用户要求研究"Graph Neural Networks在分子属性预测中的最新进展", 传统模式下:
- LLM给出一次性综述, 但引用的论文可能不存在 (幻觉)
- 无法验证提出的方法是否真的优于baseline
- 没有迭代修正, 第一版就是最终版

### 1.2 现有方案的局限性

#### 方案1: LLM单轮回答模式
- **优点**: 速度快, 交互简单
- **缺点**: 无实验验证, 易产生幻觉, 不可迭代

#### 方案2: RAG增强回答模式
- **优点**: 有文献支撑, 减少幻觉
- **缺点**: 仍然是单轮, 无法执行实验验证假设

#### 方案3: 人工研究流程
- **优点**: 高质量, 有实验, 可迭代
- **缺点**: 耗时数周到数月, 成本高

### 1.3 创新方案: 7阶段迭代闭环

受自动化科学发现 (Automated Scientific Discovery) 理念启发, 我们提出 **7阶段迭代闭环架构**:

- **闭环反馈**: 实验结果反馈到文献检索和假设修正
- **真实执行**: 实验代码在Docker沙箱中真实执行, 产出量化指标
- **有限收敛**: 最大迭代次数硬限制, 三路决策 (iterate/pivot/conclude) 保证收敛
- **证据驱动**: 每个假设必须有文献支撑, 每个结论必须有实验证据

## 2. 功能需求

### 2.1 领域探索功能 (FR-001)

**需求描述**: 系统应能够对给定的研究课题进行领域探索, 发现关键方向.

**功能点**:
- 通过 Brave Web Search 搜索领域最新进展
- LLM 分析搜索结果, 提取关键词/研究方向/核心问题
- 输出结构化的领域上下文 (关键术语, 主要研究方向, 核心问题)

**验收标准**:
- [ ] 给定任意研究课题, 能产出至少 3 个研究方向
- [ ] 领域上下文包含结构化的关键术语列表
- [ ] 搜索结果有来源溯源

### 2.2 文献检索功能 (FR-002)

**需求描述**: 系统应能够从多个学术源检索相关论文.

**功能点**:
- arXiv API 关键词/分类检索
- Semantic Scholar API 论文检索 + 引用图谱
- Brave Web Search 补充检索
- 论文去重与相关性排序
- 输出结构化论文列表 (标题/摘要/作者/年份/引用数/URL)

**验收标准**:
- [ ] 能从 arXiv 和 Semantic Scholar 同时检索
- [ ] 论文列表按相关性排序
- [ ] 去重逻辑正确 (基于 DOI 或标题)
- [ ] 每次检索返回 10-30 篇相关论文

### 2.3 知识综合功能 (FR-003)

**需求描述**: 系统应能够综合文献发现, 识别知识 gap 和研究机会.

**功能点**:
- LLM 综合多篇论文摘要, 提取共性发现
- 识别矛盾观点和未解决问题
- 生成研究假设列表
- 更新领域知识图谱

**验收标准**:
- [ ] 综合报告覆盖收集到的所有论文
- [ ] 至少生成 1-3 个可验证的假设
- [ ] 识别的 gap 与实际文献内容一致

### 2.4 实验设计功能 (FR-004)

**需求描述**: 系统应能够基于假设生成可执行的实验方案.

**功能点**:
- LLM 生成实验方案 (目标/方法/指标/预期结果)
- 生成可执行的 Python 实验代码
- 指定实验依赖 (pip packages)
- 定义成功/失败判定标准

**验收标准**:
- [ ] 实验代码语法正确, 可独立运行
- [ ] 实验有明确的评价指标
- [ ] 依赖列表完整

### 2.5 实验执行功能 (FR-005)

**需求描述**: 系统应能够在隔离沙箱中执行实验代码.

**功能点**:
- Docker 容器隔离执行
- 资源限制 (CPU 1核, 内存 2GB, 超时 300s)
- 捕获 stdout/stderr/退出码
- 收集产出文件 (JSON 报告, CSV 数据)
- 超时自动终止

**验收标准**:
- [ ] 实验代码在隔离环境中执行, 不影响宿主系统
- [ ] 超时后自动终止并报告
- [ ] stdout/stderr 完整捕获
- [ ] 资源限制生效

### 2.6 结果分析功能 (FR-006)

**需求描述**: 系统应能够分析实验结果, 验证或推翻假设.

**功能点**:
- 解析实验输出 (JSON/文本/数值)
- LLM 分析结果与假设的关系
- 生成分析报告 (关键发现, 假设验证状态, 改进建议)

**验收标准**:
- [ ] 能正确解析实验产出的 JSON 报告
- [ ] 假设验证状态 (confirmed/rejected/inconclusive) 判定合理
- [ ] 分析报告包含具体数据支撑

### 2.7 迭代决策功能 (FR-007)

**需求描述**: 系统应能够基于分析结果决定下一步行动.

**功能点**:
- 评估当前研究进度和质量
- 三种决策: iterate (继续调优), pivot (改变方向), conclude (生成报告)
- iterate: 生成具体的调整方向, 回到 Survey 或 Design
- pivot: 重新探索领域, 回到 Scout
- conclude: 汇总所有迭代结果, 生成最终研究报告

**验收标准**:
- [ ] 迭代上限 (默认5次) 内必须收敛到 conclude
- [ ] iterate 决策包含具体的调整方向
- [ ] 最终报告包含完整的研究日志

## 3. 非功能需求

### 3.1 安全性 (NFR-001)

- 实验代码在 Docker 隔离容器中执行
- 资源限制: CPU 1核, 内存 2GB, 超时 300s
- 禁止网络访问 (实验阶段), 除非显式允许

### 3.2 可观测性 (NFR-002)

- 所有 LLM 调用通过 Langfuse 追踪
- 研究日志持久化 (PostgreSQL checkpoint)
- 结构化日志 (structlog) 覆盖所有关键路径

### 3.3 成本控制 (NFR-003)

- 每个研究会话的 LLM token 预算上限
- 迭代次数硬限制 (默认5次)
- 文献检索结果数量限制

### 3.4 可扩展性 (NFR-004)

- 支持后续添加新的学术数据源
- 实验类型可扩展 (Python/Shell/Jupyter)
- 沙箱引擎可替换 (Docker/subprocess)

## 4. 验收标准

### 4.1 功能验收标准

#### AC-1: 领域探索验收

- [ ] 给定任意课题, 能产出至少3个研究方向
- [ ] 领域上下文包含结构化的关键术语列表 (>=5个)
- [ ] refined_queries可直接用于文献检索
- [ ] Brave不可用时fallback正常工作

#### AC-2: 文献检索验收

- [ ] arXiv和Semantic Scholar并行检索
- [ ] 论文按相关性排序
- [ ] DOI/arXiv ID/标题三级去重正确
- [ ] 单次检索返回10-30篇相关论文
- [ ] 单个数据源失败不影响其他源

#### AC-3: 知识综合验收

- [ ] 综合报告覆盖Top 20论文
- [ ] 生成1-3个可测试的假设
- [ ] 假设包含statement, rationale, supporting_papers
- [ ] 识别的gap与文献内容一致

#### AC-4: 实验设计验收

- [ ] 实验代码为合法Python, 语法正确
- [ ] 实验有明确的评价指标 (expected_metrics)
- [ ] 依赖列表完整 (dependencies)
- [ ] 成功判定标准明确 (success_criteria)

#### AC-5: 实验执行验收

- [ ] Docker模式下实验在隔离容器中执行
- [ ] subprocess fallback正常工作 (Docker不可用时)
- [ ] 超时 (300s) 后自动终止, exit_code=124
- [ ] stdout/stderr完整捕获 (截断至10000/5000字符)
- [ ] JSON metrics从stdout最后一行正确解析

#### AC-6: 结果分析验收

- [ ] 能正确解析JSON格式的实验输出
- [ ] 假设状态判定合理 (confirmed/rejected/inconclusive)
- [ ] 分析报告包含具体数据支撑
- [ ] 改进建议可操作

#### AC-7: 迭代决策验收

- [ ] max_iterations内必须收敛到conclude
- [ ] iterate决策包含具体的调整方向
- [ ] pivot决策回到Scout重新探索
- [ ] 最终报告包含完整研究日志和迭代记录

### 4.2 质量验收标准

#### AC-8: 闭环完整性

- [ ] 每次迭代经过完整的 Survey→Synthesize→Design→Experiment→Analyze→Decide 流程
- [ ] 实验结果反馈到下一轮的假设修正
- [ ] 研究日志 (JournalEntry) 覆盖每个阶段

#### AC-9: 报告质量

- [ ] 最终报告包含: 研究主题, 文献综述, 假设列表, 实验结果, 关键发现
- [ ] 报告中的数据与实际实验结果一致
- [ ] 报告结构清晰, 可读性强

### 4.3 性能验收标准

#### AC-10: 性能验收

- [ ] 单次迭代耗时 < 5分钟 (含实验执行)
- [ ] 5次迭代总耗时 < 30分钟
- [ ] 每次LLM调用 < 30秒
- [ ] 文献检索 (arXiv + S2) < 30秒

### 4.4 可靠性验收标准

#### AC-11: 错误处理

- [ ] 任何单个阶段失败不中断整体流程
- [ ] LLM调用失败时有fallback逻辑
- [ ] 外部API (arXiv/S2/Brave) 超时有重试或fallback
- [ ] 沙箱崩溃正确报告, 不影响宿主

## 5. 约束条件

### 5.1 技术约束

- 必须使用LangGraph StateGraph进行研究流程编排
- 必须使用structlog进行结构化日志记录
- 必须使用Langfuse追踪所有LLM调用
- 必须使用AsyncPostgresSaver进行状态检查点持久化
- 实验代码必须在Docker隔离环境中执行 (fallback到subprocess)

### 5.2 架构约束

- Worker节点 (各研究阶段Agent) 只返回Dict, 不使用Command.goto
- 只有ResearchGateway使用Command.goto进行路由
- ResearchGraph与PipelineGraph完全独立, 无共享State
- 复用现有基础设施 (LLMService, BraveSearchClient, DB连接池)

### 5.3 数据约束

- Paper必须有去重标识 (DOI/arXiv ID/标题)
- Hypothesis必须有唯一hypothesis_id
- Experiment必须有唯一experiment_id
- ResearchState的Reducer必须支持幂等合并

### 5.4 安全约束

- 沙箱内存限制: 2GB
- 沙箱CPU限制: 1核
- 沙箱超时: 300秒
- 沙箱网络: 默认隔离 (`--network=none`)

## 6. 依赖关系

### 6.1 上游依赖

无直接上游Agent依赖. ResearchGraph是独立入口.

### 6.2 下游依赖

- **用户**: 通过Research API端点消费研究结果
- **潜在集成**: 未来可将研究报告注入主PipelineGraph作为高质量evidence

### 6.3 外部服务依赖

| 服务 | 必要性 | 失败影响 |
|------|--------|---------|
| arXiv API | 推荐 | 丢失预印本论文源, S2和Brave可补充 |
| Semantic Scholar API | 推荐 | 丢失引用图谱和同行评审论文, arXiv和Brave可补充 |
| Brave Web Search | 推荐 | Scout阶段无Web数据, LLM用自身知识fallback |
| LLM Service | 必须 | 所有阶段依赖LLM, 失败则研究中断 |
| Docker Engine | 推荐 | 实验无隔离, fallback到subprocess |
| PostgreSQL | 推荐 | 无状态检查点, 研究不可恢复 |

### 6.4 基础设施依赖

- LLM服务 (llm_service) — 所有LLM调用
- 提示词管理 (app/prompts/) — 6个研究阶段提示词
- 配置管理 (Settings) — 9个RESEARCH_*配置项
- 日志服务 (structlog logger) — 结构化日志
- Langfuse — LLM可观测性追踪

## 7. 系统架构

### 7.1 研究图阶段流转

```
Scout -> Survey -> Synthesize -> Design -> Experiment -> Analyze -> Decide
                                                                      |
                                              iterate: -> Survey/Design
                                              pivot:    -> Scout
                                              conclude: -> ReportAssembly -> END
```

### 7.2 与现有系统的关系

- **独立图**: ResearchGraph 与现有 PipelineGraph 完全隔离
- **复用基础设施**: BraveSearchClient, LLM Service, PostgreSQL, Langfuse
- **遵循架构约束**: Worker 不路由, 只有 ResearchGateway 使用 Command.goto

### 7.3 新增组件

| 层级 | 组件 | 说明 |
|------|------|------|
| 基础设施 | ArxivClient | arXiv API 异步客户端 |
| 基础设施 | SemanticScholarClient | Semantic Scholar API 异步客户端 |
| 业务层 | DomainScout | 领域探索 Agent |
| 业务层 | LiteratureSurveyor | 文献检索 Agent |
| 业务层 | KnowledgeSynthesizer | 知识综合 Agent |
| 业务层 | ExperimentDesigner | 实验设计 Agent |
| 业务层 | ExperimentRunner | 实验执行 Agent |
| 业务层 | ResultAnalyzer | 结果分析 Agent |
| 业务层 | IterationPlanner | 迭代决策 Agent |
| 业务层 | SandboxEngine | Docker 沙箱引擎 |
| 编排层 | ResearchGraph | 研究 LangGraph |
| 编排层 | ResearchGateway | 研究路由节点 |
| 表现层 | Research API | 研究 API 端点 |

## 8. 术语表

| 术语 | 英文 | 定义 |
|------|------|------|
| 研究闭环 | Research Loop | 完整的研究循环: 探索→检索→综合→实验→分析→决策 |
| 领域上下文 | Domain Context | Scout阶段产出的结构化领域知识 (关键词, 方向, 问题) |
| 假设 | Hypothesis | 可测试的研究命题, 需实验验证, 含statement/rationale/status |
| 实验 | Experiment | 含可执行Python代码和评价指标的测试方案 |
| 沙箱 | Sandbox | 隔离的代码执行环境 (Docker/subprocess) |
| 迭代决策 | Iteration Decision | iterate(继续调优)/pivot(换方向)/conclude(结束) |
| 研究日志 | Research Journal | 按时间排序的阶段执行日志 (JournalEntry列表) |
| 迭代记录 | Iteration Record | 每轮迭代的决策和关键发现摘要 |
| 去重Key | Dedup Key | 论文去重标识, 优先级: DOI > arXiv ID > 标题 |
