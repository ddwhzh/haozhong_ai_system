## 1. 项目背景

### 1.1 行业现状

当前AI Agent开发领域正处于快速发展期, 但面临诸多技术挑战。传统的单Agent架构在处理复杂任务时存在能力边界, 而多Agent协同系统虽然理论上具备更强能力, 但在实际落地中缺乏成熟的工程化方案。本项目的目标是在生产环境中构建一个可扩展、可观测、可维护的多Agent协同系统。

### 1.2 核心困境分析

当前AI Agent开发领域面临以下核心困境:

| 编号 | 困境 | 详细描述 | 影响 | 实际案例 |
|------|------|---------|------|---------|
| **P1** | Agent开发架构缺乏成熟方案 | 业界缺乏统一的分层架构标准, 业务逻辑、编排逻辑、基础设施耦合严重, 导致代码难以维护和扩展。新功能开发需要修改多个模块, 测试成本高, 迭代周期长。 | 开发迭代效率低, 模块化管理困难, 团队协作成本高, 代码质量难以保证 | 某项目新增一个Agent需要修改15个文件, 涉及3个不同层级, 导致回归测试耗时2周 |
| **P2** | 多Agent算法架构不好优化 | Agent间缺乏标准化的通信机制, 信息传递依赖临时约定的数据结构, 难以追踪信息流转路径。Agent执行顺序硬编码, 无法动态调整, 导致资源浪费和性能瓶颈。 | Agent间协同效果差, 信息传递不准确, 调试困难, 性能优化空间受限 | 某系统3个Agent串行执行, 总耗时15分钟, 其中等待时间占60%, 无法并行化 |
| **P3** | 检索信息存在多跳较深推理的问题 | 单一向量检索无法处理需要多步推理的复杂查询, 例如"某公司2024年Q3财报中提到的风险因素对股价的影响"。传统RAG只能返回文档片段, 无法理解实体间的深层关联关系。 | 无法有效处理需要多步推理的复杂查询, 检索结果碎片化, 缺乏上下文连贯性 | 用户查询"A公司收购B公司后对C行业的影响", 系统只能返回3个不相关的文档片段, 无法串联成完整答案 |
| **P4** | 生成各项结果的粒度不一致 | LLM自由生成模式下, 不同部分的详略程度差异巨大。例如生成报告时, 某些章节500字, 某些章节50字, 缺乏统一的结构化约束。模板化方案又过于僵化, 无法适应动态内容需求。 | 输出质量不可控, 各部分详略不均, 用户体验差, 难以进行自动化评估 | 某系统生成的报告共10个章节, 其中3个章节内容完整(800+字), 5个章节仅标题(20字), 2个章节缺失 |
| **P5** | 向量检索对细粒度相似度识别较差且存在对称性问题 | 余弦相似度具有对称性: cos(A,B) = cos(B,A), 但在评估场景中,"A是否忠实于B"和"B是否忠实于A"是完全不同的语义。高维embedding空间中, 大多数向量对的余弦相似度集中在0.7-0.9区间, 区分度不足。 | 评估不准确, 无法驱动自动化优化, 误判率高, 无法识别细微的质量差异 | 某评估系统对95%的生成内容给出0.85-0.90的相似度分数, 无法区分优质内容和中等质量内容 |

### 1.3 项目目标

本项目旨在构建一个生产级的多Agent协同系统, 通过以下创新解决上述困境:

1. **四层管理式金字塔架构**: 明确分层职责, 实现高内聚低耦合
2. **LangGraph状态机编排**: 基于有纪律的状态机实现可预测的执行流程
3. **证据图通信机制**: 通过Belief+Intent实现Agent间的标准化信息交换
4. **RAG+KG并行检索**: 广度检索与深度检索相结合, 解决多跳推理问题
5. **Proposal-based生成**: Fast RCNN启发的结构化生成, 保证粒度一致性
6. **匈牙利匹配评估**: DETR启发的非对称评估, 解决对称性问题

## 2. 需求目标

### 2.1 架构需求

#### NR-1: 采用管理式金字塔架构

**需求描述**: 将系统划分为表现层(Presentation)、编排层(Orchestration)、业务工作层(Business Worker)、基础设施层(Infrastructure)四层, 每层职责明确, 自上而下单向依赖。

**详细要求**:
- 表现层(`app/presentation/`): 负责HTTP请求处理、Schema验证、流式响应、错误处理。禁止包含任何业务逻辑。
- 编排层(`app/orchestration/`): 负责LangGraph图定义、路由决策、状态管理、阶段转换。禁止包含检索/生成/评估的具体算法逻辑。
- 业务工作层(`app/agents/`): 负责三个Agent的核心AI逻辑(检索、生成、评估)。禁止使用`Command.goto`进行路由。
- 基础设施层(`app/infra/`): 负责数据库连接、KG查询、向量存储、LLM服务调用。禁止包含业务决策逻辑。

**验收标准**:
- [ ] 所有层级的代码严格遵循目录结构, 无跨层直接调用(必须通过接口)
- [ ] 表现层代码中无任何LLM调用、数据库查询、KG查询逻辑
- [ ] 编排层代码中无任何检索算法、生成算法、评估算法实现
- [ ] 业务工作层代码中无任何路由逻辑(不使用`Command.goto`)
- [ ] 基础设施层代码中无任何业务决策逻辑
- [ ] 代码审查通过率100%, 无架构违规

**优先级**: Must Have

---

#### NR-2: 基于LangGraph框架实现编排

**需求描述**: 使用LangGraph作为Agent编排框架(非LangChain Agent), 实现状态机驱动的执行流程, 支持checkpoint持久化和HITL中断。

**详细要求**:
- 使用`StateGraph`构建有纪律的状态机: Explore → Freeze → Plan → Execute → Validate → Done/Rollback
- 实现`AsyncPostgresSaver`进行checkpoint持久化, 支持断点续传
- 支持`interrupt_before`机制实现HITL人工审核
- Gateway节点是唯一允许使用`Command.goto`的节点, 所有路由决策集中在此

**验收标准**:
- [ ] LangGraph图成功编译, 无循环依赖
- [ ] 状态机转换符合设计文档, 无非法状态跳转
- [ ] Checkpoint持久化正常工作, 服务重启后可恢复执行
- [ ] HITL中断机制正常工作, 可在指定节点暂停等待人工输入
- [ ] Gateway节点外的所有节点均不使用`Command.goto`
- [ ] 状态机执行日志完整, 可追溯每个阶段的输入输出

**优先级**: Must Have

---

#### NR-3: 提升系统的可维护性和扩展性

**需求描述**: 通过清晰的架构设计和标准化接口, 使系统易于维护和扩展。新增Agent或修改现有Agent不应影响其他组件。

**详细要求**:
- 所有Agent实现统一的`BaseAgent`接口, 遵循相同的I/O契约(`AgentInput`/`AgentOutput`)
- 核心类型系统位于`app/core/types/`, 被所有层共享
- 配置管理使用Pydantic Settings, 支持环境变量和配置文件
- 日志使用structlog, 统一格式, 支持结构化查询

**验收标准**:
- [ ] 新增一个Agent只需实现`BaseAgent`接口, 无需修改其他Agent代码
- [ ] 修改检索Agent的实现不影响生成Agent和评估Agent
- [ ] 配置变更通过环境变量即可生效, 无需修改代码
- [ ] 日志查询支持按session_id、agent_name、phase等维度过滤
- [ ] 代码覆盖率≥80%, 关键路径100%覆盖
- [ ] 文档完整, 包含架构设计、API文档、部署指南

**优先级**: Must Have

### 2.2 多Agent协同需求

#### NR-4: 采用多Agent分阶段设计

**需求描述**: 区分检索Agent(RetrievalAgent)、生成Agent(GenerationAgent)、评估Agent(EvaluationAgent)三个独立阶段, 每个阶段职责单一, 通过证据图进行信息交换。

**详细要求**:
- 检索Agent: 负责查询分解、向量检索、KG检索、结果融合, 输出检索证据到证据图
- 生成Agent: 负责proposal生成、槽位提取、内容生成, 从证据图读取检索结果, 输出生成内容到证据图
- 评估Agent: 负责质量评分、匈牙利匹配、prompt优化, 从证据图读取生成内容, 输出评估结果到证据图

**验收标准**:
- [ ] 三个Agent可独立测试, 互不依赖
- [ ] Agent间通信100%通过证据图, 无直接函数调用
- [ ] 每个Agent的输出包含完整的Belief和Intent信息
- [ ] 证据图中的节点和边关系清晰, 可追溯完整推理链
- [ ] 单个Agent故障不影响其他Agent的执行(通过错误处理机制)

**优先级**: Must Have

---

#### NR-5: 引入Human-In-The-Loop模式

**需求描述**: 在关键决策点支持人工介入审核, 确保输出质量符合业务要求。HITL模式可配置启用/禁用。

**详细要求**:
- 在评估完成后, 如果质量分数处于边界区间(例如0.6-0.8), Gateway路由到`human_review`节点
- 使用LangGraph的`interrupt_before`机制, 管道暂停等待人工输入
- 提供REST API `/api/v1/agent/review`供人工提交审核决策
- 支持三种操作: approve(通过)、reject(打回重生成, 附带反馈)、edit(直接修改证据图)

**验收标准**:
- [ ] HITL中断机制正常工作, 管道在指定节点暂停
- [ ] 人工审核API响应时间<100ms, 支持并发审核
- [ ] 审核决策正确传递回管道, 管道可恢复执行
- [ ] 审核历史记录完整, 可查询每次审核的决策和反馈
- [ ] HITL模式可通过配置开关控制, 默认启用
- [ ] 审核超时机制: 如果24小时内无人工响应, 自动采用默认策略(approve或reject)

**优先级**: Should Have

---

#### NR-6: 通过带有belief+intent的证据图实现Agent之间的交互对齐

**需求描述**: 所有Agent通过共享的证据图(EvidenceGraph)进行通信, 每个证据节点包含Belief(置信度)和Intent(意图声明), 确保信息传递的准确性和可追溯性。

**详细要求**:
- Belief: 量化Agent对证据的信任程度, 取值[0, 1], 包含source_agent和supporting_evidence_ids
- Intent: 声明证据被产生的目的, 例如RETRIEVE、GENERATE、EVALUATE等, 包含description和target_agent
- 证据图为append-only结构, Agent只能新增节点/边, 不能删除
- 边关系类型包括: DERIVED_FROM、DECOMPOSES_TO、FUSED_INTO、EVALUATED_BY、SUPPORTS等

**验收标准**:
- [ ] 每个证据节点必须包含Belief和Intent, 创建时强制校验
- [ ] 证据图支持O(1)节点查找, 支持按content_type、intent_type、source_agent过滤
- [ ] 通过边关系可追溯任何结论的完整推理链
- [ ] 证据图序列化/反序列化正常, 支持持久化到数据库
- [ ] 证据图可视化工具可展示节点和边的关系图
- [ ] 证据图大小限制: 单次管道运行最多1000个节点, 超出时触发告警

**优先级**: Must Have

### 2.3 检索Agent需求

#### NR-7: QDMR查询分类 + Query分解 + 树形探索

**需求描述**: 基于QDMR(Question Decomposition Meaning Representation)对输入查询进行8类分类, 再根据分类结果进行类型感知的有序分解, 最后通过树形探索器逐步骤检索, 支持分支级回退机制。

**详细要求**:
- **查询分类(QueryClassifier)**: 使用LLM将查询分为8个QDMR类别:
  - QSelect(简单事实查询): 主策略RAG
  - QFilter(条件过滤查询): 主策略RAG+metadata过滤
  - QChain(链式推理查询): 主策略KG多跳
  - QComposition(组合查询): 主策略分解为子树
  - QComparison(比较查询): 主策略RAG+KG并行
  - QAggregation(聚合/排序查询): 主策略KG+结构化
  - QBoolean(是否判断查询): 主策略RAG快速验证
  - QUnion(联合/交叉查询): 主策略多分支RAG+KG合并
- **QDMR分解(QueryDecomposer.qdmr_decompose)**: 根据QType生成有序步骤(TreeStep), 每步含question, operator, retrieval_strategy, depends_on
- **树形探索(TreeExplorer)**: 逐步骤执行检索, 每步先试主策略, 质量低于阈值时回退到备选策略
- 回退阈值(`RETRIEVAL_BACKTRACK_THRESHOLD`, 默认0.4), 最大回退次数(`RETRIEVAL_MAX_BRANCH_RETRIES`, 默认1)
- LLM调用失败时降级策略: 分类默认QComposition, 分解默认单步select

**验收标准**:
- [ ] 查询分类覆盖8个QDMR类别, 输出包含q_type, confidence, reasoning
- [ ] QDMR分解生成有序步骤, 步骤间依赖关系正确(depends_on)
- [ ] 树形探索逐步骤执行, 主策略失败时自动回退到备选策略
- [ ] 回退机制正常工作, 分支质量评估基于节点置信度均值
- [ ] 降级策略正常工作, LLM失败时系统仍可继续执行
- [ ] 检索结果包含分类元数据(q_type, strategy)和树步骤元数据(step_idx, operator)
- [ ] 向量检索响应时间<500ms(单次查询), 支持并发检索
- [ ] 检索结果去重机制: 相同文档片段只保留置信度最高的

**优先级**: Must Have

---

#### NR-8: 采用知识图谱的BFS模式实现深度式查询

**需求描述**: 对每个子查询执行Neo4j知识图谱的BFS多跳遍历, 深入挖掘实体间的关联关系, 解决多跳推理问题。

**详细要求**:
- 从子查询中提取实体和关系, 在Neo4j中执行BFS遍历, 最大跳数可配置(默认3跳)
- 将BFS路径转换为可读的推理链, 每个推理链包含: 起始实体 → 关系1 → 中间实体 → 关系2 → 目标实体
- 推理链的置信度随跳数衰减: confidence = 0.95^depth
- 将长推理链拆分为多个子图, 每个子图包含2-3个节点, 便于下游Agent理解

**验收标准**:
- [ ] BFS遍历响应时间<2s(单次查询, 3跳以内)
- [ ] 推理链拆分正确, 每个子图可独立理解
- [ ] 置信度衰减公式正确应用, 3跳路径的置信度≈0.86
- [ ] 推理链节点通过DERIVED_FROM边连接到子查询节点
- [ ] 支持Cypher查询自定义, 可配置关系类型过滤
- [ ] KG检索结果与向量检索结果在证据图中可区分(content_type不同)

**优先级**: Must Have

---

#### NR-9: 通过查询子图拆分推理链子图, 保证Agent能读懂推理链

**需求描述**: 将复杂的多跳推理链拆分为多个可读的子图, 每个子图包含2-3个节点和1-2条边, 确保下游Agent能够理解推理过程。

**详细要求**:
- 识别推理链中的关键节点(实体)和边(关系)
- 按照语义连贯性将长链拆分为多个子图
- 每个子图包含: 起始节点、关系、目标节点、置信度、跳数信息
- 子图之间通过边关系连接, 形成完整的推理路径

**验收标准**:
- [ ] 推理链拆分算法正确, 5跳路径拆分为2-3个子图
- [ ] 子图内容可读性强, 人工审核通过率≥90%
- [ ] 子图节点包含完整的元数据(实体类型、关系类型、置信度)
- [ ] 子图在证据图中的表示清晰, 可通过可视化工具展示
- [ ] 拆分后的子图数量合理, 不会过度拆分导致信息碎片化

**优先级**: Should Have

---

#### NR-10: 通过Cascade模式实现多轮查询结果的智能融合

**需求描述**: 对向量检索结果和KG检索结果进行多轮迭代融合, 生成综合的检索证据, 提高检索质量。

**详细要求**:
- 第一轮: 融合向量检索的top_k结果和KG检索的推理链
- 后续轮次: 基于融合结果生成新的查询, 执行补充检索
- 使用LLM进行融合, 输出融合后的证据和completeness分数
- 当completeness ≥ 0.85时提前终止, 最多执行3轮
- 融合结果通过FUSED_INTO边连接到所有源节点

**验收标准**:
- [ ] Cascade融合平均执行1.5-2轮, completeness达到0.85以上
- [ ] 融合结果质量提升明显, 人工评估通过率提升20%以上
- [ ] 融合响应时间<3s(单轮), 总耗时<8s(3轮)
- [ ] 融合结果包含完整的来源追溯信息
- [ ] 提前终止机制正常工作, 避免不必要的LLM调用
- [ ] 融合失败时降级策略: 返回原始检索结果的并集

**优先级**: Should Have

### 2.4 生成Agent需求

#### NR-11: 借鉴Fast RCNN思想, 生成多个同类型的proposal, 通过证据图槽位填空实现生成

**需求描述**: 将生成任务分解为多个结构化的proposal, 每个proposal定义需要填充的槽位(slots), 从证据图中提取信息填充槽位, 而非自由生成。

**详细要求**:
- Proposal生成阶段(类比Fast RCNN的RPN): 使用LLM生成N个同类型的proposal, 每个proposal包含aspect、question、template、slots字段
- 槽位提取阶段(类比Fast RCNN的ROI Head): 对每个proposal, 从证据图中提取信息填充slots
- 所有proposal共享相同的结构, 确保输出粒度一致
- Proposal节点通过SUPPORTS边连接到相关证据节点

**验收标准**:
- [ ] Proposal生成数量可配置, 默认5-10个, 每个proposal包含3-5个slots
- [ ] 槽位提取准确率≥85%, 从证据图中找到匹配信息的比例
- [ ] 生成内容结构一致, 人工评估粒度一致性得分≥0.9
- [ ] Proposal生成响应时间<2s, 槽位提取响应时间<1s(单个proposal)
- [ ] 槽位提取失败时处理机制: 标记为"insufficient evidence", 不阻塞整体流程
- [ ] 生成内容包含置信度信息, 基于槽位填充的完整程度

**优先级**: Must Have

#### NR-12: 将复杂的生成任务转化为从证据图中提取信息的填空任务(非模板自由生成)

**需求描述**: 生成Agent不进行自由文本生成, 而是基于proposal模板从证据图中提取信息, 确保生成内容有据可依。

**详细要求**:
- Proposal模板定义固定的结构, 例如: "## {aspect}\n\n**Q:** {question}\n\n**A:** {slot1} {slot2} {slot3}"
- 从证据图中搜索匹配的节点, 提取content填充到对应slot
- 支持多个证据节点填充同一个slot, 进行信息融合
- 如果某个slot无法找到匹配证据, 标记为"insufficient evidence"

**验收标准**:
- [ ] 生成内容100%来自证据图, 无自由生成内容
- [ ] 槽位填充准确率≥85%, 提取的信息与证据图内容一致
- [ ] 多证据融合机制正常工作, 相同slot的多个证据正确合并
- [ ] "insufficient evidence"标记正确, 不影响其他slot的填充
- [ ] 生成内容可追溯, 每个slot可追溯到对应的证据节点
- [ ] 生成响应时间<5s(10个proposal), 支持并发处理

**优先级**: Must Have

#### NR-13: 所有proposal共享相同结构(aspect + question + slots), 确保生成结果的粒度一致性

**需求描述**: 所有proposal遵循统一的结构定义, 确保最终输出的各个部分详略程度一致, 提升用户体验。

**详细要求**:
- Proposal结构: {proposal_type, aspect, question, template, slots: [{slot_name, slot_type, evidence_hint}]}

- Slots数量控制在3-5个, 每个slot的提取内容长度相近
- 最终输出时, 各个proposal生成的内容长度差异不超过20%

**验收标准**:
- [ ] Proposal结构验证通过, 100%的proposal符合结构定义
- [ ] 生成内容长度统计: 各proposal内容长度标准差<均值×0.2
- [ ] 人工评估粒度一致性得分≥0.9(1-5分制, 5分为完全一致)
- [ ] 输出格式统一, 各proposal的markdown格式一致
- [ ] 结构一致性检查自动化, CI/CD中集成检查脚本

**优先级**: Must Have

### 2.5 评估Agent需求

#### NR-14: 通过自监督去噪以及加入稀疏矩阵来重新设计得分函数

**需求描述**: 解决向量相似度的对称性问题和细粒度区分度不足的问题, 设计非对称的评估得分函数。

**详细要求**:
- Dense分量: 使用自监督去噪技术, 去除公共噪声方向, 保留区分性信息。对embedding进行PCA降维, 去除前k个主成分(公共噪声), 计算去噪后的余弦相似度
- Sparse分量: 使用类BM25的非对称词项重叠得分, 计算生成内容中的词项在参考内容中的出现频率
- 组合公式: score = alpha × dense_denoised + (1-alpha) × sparse, alpha可配置(默认0.7)
- 得分范围[0, 1], 支持细粒度区分

**验收标准**:
- [ ] 得分函数非对称性验证: score(A→B) ≠ score(B→A)的比例≥80%
- [ ] 得分分布合理, 不再集中在0.7-0.9区间, 标准差≥0.15
- [ ] 得分计算响应时间<200ms(单次评估)
- [ ] 自监督去噪参数可配置(k值), 默认去除前10个主成分
- [ ] Sparse分量计算正确, BM25公式实现准确
- [ ] 得分函数在测试集上的区分度提升≥30%

**优先级**: Must Have

---

#### NR-15: 采用DETR的匈牙利匹配思想实现自动化评估

**需求描述**: 使用匈牙利算法进行最优二部图匹配, 将生成的proposal与参考标准进行匹配, 计算faithfulness和completeness分数。

**详细要求**:
- 构建二部图: 左侧节点为生成的proposal, 右侧节点为参考标准section
- 边权重: 使用重新设计的得分函数计算proposal与section的匹配分数
- 使用scipy.optimize.linear_sum_assignment求解最优匹配
- 计算匹配后的faithfulness_rate和completeness_rate
- 未匹配的proposal和section分别计算penalty分数

**验收标准**:
- [ ] 匈牙利匹配算法正确实现, 求解时间<1s(100个节点)
- [ ] 匹配结果合理, 人工审核通过率≥85%
- [ ] Faithfulness_rate和completeness_rate计算正确, 范围[0, 1]
- [ ] 未匹配处理机制: 未匹配的proposal标记为"hallucination", 未匹配的section标记为"missing"
- [ ] 匹配结果可追溯, 每个匹配对可查看详细得分
- [ ] 支持部分匹配: 一个proposal可匹配多个section(如果得分都高)

**优先级**: Must Have

---

#### NR-16: 为后续自动化调整prompt以及架构奠定基础

**需求描述**: 评估结果不仅用于质量判断, 还用于驱动自动化优化。识别弱环节, 生成prompt优化建议, 为下一轮迭代提供改进方向。

**详细要求**:
- 从匈牙利匹配结果中识别弱section: 低分(<0.6)、不忠实、未匹配
- 调用LLM诊断问题根因: 幻觉、缺上下文、粒度错误、模板不当等
- 生成prompt patch: 针对system_prompt、proposal_template、extraction_template分别生成修改建议
- 将优化建议存为EvidenceNode, content_type="prompt_optimization", 供后续迭代使用
- 预测每个patch的期望改善幅度, 优先应用高价值patch

**验收标准**:
- [ ] 弱环节识别准确率≥80%, 人工审核确认的弱环节被正确识别
- [ ] 问题诊断准确率≥70%, LLM诊断的根因与人工判断一致
- [ ] Prompt patch生成成功率≥90%, 生成的patch语法正确、语义清晰
- [ ] 优化建议存储正确, 可在下一轮迭代中读取和应用
- [ ] 自动化优化闭环: 应用patch后, 下一轮评估分数提升≥5%
- [ ] 优化历史可追溯, 记录每次优化的patch和效果

**优先级**: Should Have

## 4. 约束条件

### 4.1 技术栈约束

- **Python版本**: 必须使用Python 3.13+, 不支持3.12及以下版本
- **数据库驱动**: PostgreSQL必须使用psycopg3(psycopg[binary,pool]≥3.3.2), 所有SQL查询必须使用%s参数占位符, 禁止字符串拼接
- **Agent编排**: 必须使用LangGraph作为编排框架, 禁止使用LangChain Agent
- **LLM服务**: 支持OpenAI API和OpenAI兼容API(如智谱GLM), 通过OPENAI_API_BASE配置
- **知识图谱**: 必须使用Neo4j 5.x版本, 使用Cypher查询语言
- **向量存储**: 必须使用PGVector(PostgreSQL扩展), 与主数据库共享基础设施

### 4.2 架构约束

- **路由约束**: Worker节点(Agent)禁止使用`Command.goto`, 只有Gateway节点可以路由
- **证据图约束**: 证据图为append-only结构, Agent只能新增节点/边, 不能删除已有节点
- **通信约束**: 所有Agent间通信必须通过证据图(EvidenceGraph), 禁止Agent间直接函数调用
- **状态管理**: 所有状态变更必须通过LangGraph的State机制, 禁止使用全局变量或单例模式
- **错误处理**: 所有异步操作必须使用try-except-finally, 禁止静默吞掉异常

### 4.3 代码规范约束

- **导入规则**: 所有import语句必须在文件顶部, 禁止在函数或类内部导入
- **日志规范**: 必须使用structlog, 日志事件名必须为lowercase_with_underscores格式, 禁止使用f-string, 变量作为kwargs传递
- **重试机制**: 所有重试逻辑必须使用tenacity库, 配置指数退避策略
- **类型提示**: 所有函数签名必须包含类型提示, 使用Pydantic模型进行数据验证
- **异步规范**: 所有I/O操作(数据库、网络、文件)必须使用async/await, 禁止使用同步阻塞调用

### 4.4 性能约束

- **响应时间**: 端到端响应时间必须< 3分钟(95分位), 超过则触发告警
- **并发限制**: 单实例最大并发请求数≤ 20, 超过则返回503错误
- **资源限制**: 单次管道运行最多1000个证据节点, 超出则终止并返回错误
- **Rollback限制**: 单次管道运行最多rollback 1次, 超过则终止并返回错误
- **迭代限制**: 单次管道运行最多迭代10次, 超过则强制终止

### 4.5 部署约束

- **容器化**: 生产环境必须使用Docker部署, 禁止直接运行Python进程
- **环境变量**: 所有配置必须通过环境变量传递, 禁止硬编码配置值
- **数据库迁移**: 数据库schema变更必须通过迁移脚本, 禁止直接修改数据库
- **监控要求**: 生产环境必须启用Prometheus和Grafana监控, 禁止无监控部署

## 5. 术语定义

| 术语 | 英文 | 定义 | 使用场景 |
|------|------|------|---------|
| **Belief** | Belief | Agent对一条证据的置信度, 取值[0, 1], 包含source_agent和supporting_evidence_ids | 证据图中的每个节点都包含Belief, 用于量化Agent对证据的信任程度 |
| **Intent** | Intent | Agent产出证据的目的声明, 例如RETRIEVE、GENERATE、EVALUATE等, 包含description和target_agent | 证据图中的每个节点都包含Intent, 用于说明证据为何被产生 |
| **Evidence Graph** | Evidence Graph | 共享的证据图, 所有Agent通过它进行信息交换, 包含nodes和edges | 整个管道运行期间, 所有Agent读写证据图进行通信 |
| **EvidenceNode** | Evidence Node | 证据图中的节点, 包含evidence(content+content_type+source+metadata)、belief、intent | 检索结果、生成内容、评估结果都以EvidenceNode形式存储在证据图中 |
| **EvidenceEdge** | Evidence Edge | 证据图中的边, 连接两个节点, 关系类型包括DERIVED_FROM、DECOMPOSES_TO等 | 用于表示证据间的推导关系、拆解关系、融合关系等 |
| **Proposal** | Proposal | 生成Agent对输出任务的结构化拆解, 类比Fast RCNN的候选框, 每个proposal定义slots从证据图提取填空 | 生成Agent首先生成多个proposal, 然后对每个proposal进行槽位填充 |
| **Slot-filling** | Slot Filling | 从证据图中提取信息填充到proposal的slots中, 而非自由生成文本 | 生成Agent的核心机制, 确保生成内容有据可依 |
| **Cascade Fusion** | Cascade Fusion | 多轮迭代式检索结果融合策略, 通过LLM进行智能融合, completeness≥0.85时提前终止 | 检索Agent的最后阶段, 融合向量检索和KG检索的结果 |
| **Hungarian Matching** | Hungarian Matching | 基于匈牙利算法的二部图最优匹配, 用于评估Agent将生成内容与参考标准进行匹配 | 评估Agent的核心算法, 解决评估中的匹配问题 |
| **HITL** | Human-In-The-Loop | 人工介入审核模式, 在关键决策点暂停管道等待人工输入 | 评估完成后, 如果质量处于边界区间, 触发HITL审核 |
| **PipelinePhase** | Pipeline Phase | 管道执行阶段, 包括Explore、Freeze、Plan、Execute、Validate、Done、Rollback、Human_Review | LangGraph状态机的阶段定义, Gateway根据phase进行路由 |
| **PipelineState** | Pipeline State | LangGraph的全局状态, 包含messages、query、evidence_graph、current_phase、iteration_count等 | 整个管道运行期间的状态管理, 所有节点读写此状态 |
| **Gateway** | Gateway | 编排层的路由节点, 唯一允许使用Command.goto的节点, 根据current_phase决定下一个节点 | LangGraph图中的核心路由节点, 所有节点执行完后都回到Gateway |
| **Checkpoint** | Checkpoint | LangGraph的状态快照, 持久化到PostgreSQL, 支持断点续传 | 管道执行过程中的状态保存, 服务重启后可恢复执行 |
| **Evidence Hint** | Evidence Hint | Proposal中slot的evidence_hint字段, 提示应该从哪种类型的证据节点中提取信息 | 生成Agent进行槽位提取时的指导信息, 例如"从document_chunk或reasoning_chain中提取" |
| **Context Manifest** | Context Manifest | Freeze阶段生成的上下文清单, 包含检索结果的统计信息和关键证据摘要 | 用于Plan阶段生成proposal时的上下文信息 |
| **Faithfulness Rate** | Faithfulness Rate | 评估指标, 衡量生成内容对检索证据的忠实程度, 取值[0, 1] | 评估Agent的输出指标, 用于判断生成质量 |
| **Completeness Rate** | Completeness Rate | 评估指标, 衡量生成内容覆盖参考标准的完整程度, 取值[0, 1] | 评估Agent的输出指标, 用于判断生成完整性 |
| **Prompt Optimization** | Prompt Optimization | 自动Prompt优化, 基于评估结果识别弱环节, 生成prompt修改建议 | 评估Agent的扩展功能, 为下一轮迭代提供改进方向 |
| **Rollback** | Rollback | 验证失败时的回滚机制, 增加rollback计数, 回到Explore阶段重新检索 | 管道执行失败时的恢复机制, 最多rollback 1次 |
| **QDMR** | Question Decomposition Meaning Representation | 查询分解含义表示, 将自然语言问题分解为有序原子操作步骤的形式化方法 | 检索Agent的查询分类和分解基础, 决定检索策略 |
| **QType** | Query Type | QDMR查询类型枚举(QSelect, QFilter, QChain, QComposition, QComparison, QAggregation, QBoolean, QUnion) | QueryClassifier的输出, 决定主/备检索策略和分解深度 |
| **TreeStep** | Tree Step | QDMR分解树中的一个步骤, 包含question, operator, retrieval_strategy, depends_on | TreeExplorer的输入单元, 每个步骤独立执行检索 |
| **TreeExplorer** | Tree Explorer | 树形探索器, 逐步骤执行检索, 支持分支级回退 | 检索Agent的核心组件, 替代旧的平铺并行检索 |
| **Branch Backtrack** | Branch Backtracking | 分支级回退机制, 当某步骤的主策略质量低于阈值时, 回退到备选策略重试 | TreeExplorer中保证检索质量的关键机制 |
| **StrategyConfig** | Strategy Configuration | 检索策略配置, 包含primary_strategy, fallback_strategy, max_depth, backtrack_threshold | 每个QType对应一个StrategyConfig |

## 6. 用例场景

### 6.1 用例1: 企业财报分析查询

**场景描述**: 用户查询"某上市公司2024年Q3财报中提到的风险因素对股价的影响"。

**执行流程**:
1. **用户提交查询**: 通过REST API提交查询请求, 系统创建session并初始化证据图
2. **检索Agent执行**:
   - Query分解: 将查询拆解为3个子查询: "2024年Q3财报内容"、"风险因素列表"、"股价变动数据"
   - 向量检索: 对每个子查询执行PGVector检索, 找到相关财报文档片段
   - KG检索: 在Neo4j中执行BFS遍历, 找到"公司→发布→财报→包含→风险因素→影响→股价"的推理链
   - Cascade融合: 融合向量检索和KG检索结果, 生成综合证据
3. **Freeze阶段**: 生成context_manifest, 包含检索结果统计(找到15个文档片段、3条推理链)
4. **Plan阶段**: 生成5个proposal, 例如"财报概述"、"风险因素分析"、"股价影响评估"等
5. **Execute阶段**: 对每个proposal从证据图中提取信息填充slots, 生成结构化内容
6. **Validate阶段**: 
   - 使用重新设计的得分函数计算faithfulness和completeness
   - 使用匈牙利匹配将生成的5个proposal与参考标准进行匹配
   - 计算总体质量分数: 0.82(超过阈值0.75, 通过)
7. **Done阶段**: 组装最终输出, 返回给用户

**预期结果**: 
- 响应时间: 2分30秒
- 生成内容包含3个主要部分, 每个部分500-800字, 粒度一致
- 所有内容都有证据支撑, 可追溯到检索结果
- 质量分数0.82, 用户满意度高

**验收标准**:
- [ ] 检索到相关财报文档和推理链
- [ ] 生成内容结构完整, 粒度一致
- [ ] 所有内容可追溯到证据图
- [ ] 质量分数≥0.75
- [ ] 响应时间<3分钟

### 6.2 用例2: 技术文档生成(触发HITL)

**场景描述**: 用户查询"生成一份关于LangGraph多Agent系统的技术文档, 包含架构设计、实现细节、最佳实践"。

**执行流程**:
1. **检索Agent执行**: 检索到相关技术文档、代码示例、最佳实践指南
2. **生成Agent执行**: 生成8个proposal, 涵盖架构、实现、实践等方面
3. **评估Agent执行**: 
   - 计算质量分数: 0.68(处于边界区间0.6-0.8)
   - Gateway路由到human_review节点
   - 管道暂停, 等待人工审核
4. **HITL人工审核**: 
   - 人工查看生成内容, 发现"最佳实践"部分内容不够详细
   - 提交reject决策, 附带反馈: "最佳实践部分需要补充更多实际案例"
5. **Rollback执行**: 系统回到Explore阶段, 基于反馈补充检索"LangGraph实际案例"
6. **重新生成**: 生成Agent基于补充的检索结果重新生成"最佳实践"部分
7. **重新评估**: 质量分数提升到0.79, 通过验证
8. **Done阶段**: 返回最终文档

**预期结果**:
- HITL审核响应时间: 人工审核5分钟 + 系统重新生成2分钟 = 7分钟
- 最终生成内容质量提升, "最佳实践"部分内容充实
- 用户对最终结果满意

**验收标准**:
- [ ] HITL中断机制正常工作
- [ ] 人工审核决策正确传递
- [ ] Rollback后重新生成质量提升
- [ ] 最终质量分数≥0.75
- [ ] 总响应时间<10分钟(包含人工审核时间)

### 6.3 用例3: 复杂多跳推理查询(展示KG检索优势)

**场景描述**: 用户查询"A公司收购B公司后, 对C行业的竞争格局产生了什么影响? 请分析B公司的核心技术对C行业的影响路径"。

**执行流程**:

   - 向量检索: 找到相关新闻、财报、技术文档
   - **KG检索(关键)**:

     - 将5跳路径拆分为2个推理链子图, 便于理解
   - Cascade融合: 融合向量检索的广度信息和KG检索的深度推理
2. **生成Agent执行**: 基于融合后的证据生成结构化分析报告
3. **评估Agent执行**: 评估生成内容对复杂推理链的忠实程度
4. **Done阶段**: 返回包含完整推理路径的分析报告

**预期结果**:
- KG检索成功找到5跳推理路径, 这是向量检索无法做到的
- 生成内容包含完整的推理链条, 逻辑清晰
- 用户能够理解"收购→技术→应用→影响"的完整路径

**验收标准**:
- [ ] KG检索找到≥3跳的推理路径
- [ ] 推理链拆分为可读的子图
- [ ] 生成内容包含完整的推理链条
- [ ] 质量分数≥0.75
- [ ] 响应时间<3分钟

## 7. 优先级矩阵

### 7.1 MoSCoW优先级定义

- **Must Have (M)**: 核心功能, 系统无法运行或无法满足基本需求, 必须实现
- **Should Have (S)**: 重要功能, 显著提升用户体验或系统能力, 应该实现
- **Could Have (C)**: 可选功能, 有则更好, 无则不影响核心功能, 可以实现
- **Won't Have (W)**: 暂不实现, 未来版本考虑

### 7.2 功能需求优先级

| 需求编号 | 需求名称 | 优先级 | 理由 |
|---------|---------|--------|------|
| NR-1 | 管理式金字塔架构 | **M** | 系统架构基础, 所有功能依赖于此 |
| NR-2 | LangGraph编排 | **M** | 核心编排机制, 无此无法实现多Agent协同 |
| NR-3 | 可维护性和扩展性 | **M** | 生产系统基本要求 |
| NR-4 | 多Agent分阶段设计 | **M** | 核心功能, 系统的主要价值所在 |
| NR-5 | HITL模式 | **S** | 重要功能, 提升输出质量, 但非核心 |
| NR-6 | 证据图通信机制 | **M** | 核心通信机制, Agent协同的基础 |
| NR-7 | QDMR查询分类 + Query分解 | **M** | 检索Agent核心功能, QDMR 8类分类决定最优检索策略 |
| NR-7b | 树形探索 + 分支回退 | **M** | QDMR分解树逐步骤探索, 质量不足时自动回退到备选策略 |
| NR-8 | KG BFS检索 | **M** | 解决多跳推理问题的关键 |
| NR-9 | 推理链子图拆分 | **S** | 提升可读性, 但可通过其他方式实现 |
| NR-10 | Cascade融合 | **S** | 提升检索质量, 但非核心 |
| NR-11 | Proposal生成 | **M** | 生成Agent核心功能 |
| NR-12 | 槽位填空生成 | **M** | 确保生成内容有据可依 |
| NR-13 | 粒度一致性 | **M** | 核心质量要求 |
| NR-14 | 重新设计得分函数 | **M** | 解决评估对称性问题的关键 |
| NR-15 | 匈牙利匹配评估 | **M** | 评估Agent核心功能 |
| NR-16 | Prompt自动化优化 | **S** | 高级功能, 提升系统自适应能力 |

### 7.3 非功能性需求优先级

| 需求类别 | 优先级 | 理由 |
|---------|--------|------|
| 性能需求 | **M** | 生产系统基本要求, 响应时间过长无法接受 |
| 可靠性需求 | **M** | 系统稳定性要求, 必须保证高可用 |
| 可观测性需求 | **M** | 生产系统必须可观测, 否则无法运维 |
| 可扩展性需求 | **S** | 重要但非紧急, 初期可支持基本扩展即可 |
| 安全性需求 | **M** | 生产系统必须安全, JWT认证、输入验证等是基本要求 |
| 容器化部署需求 | **M** | 部署标准化要求, Docker Compose一键部署 |
